# Startup configuration implementation

F03 is implemented. This document covers the environment parser and the driver construction settings. The process runtime (invocation admission, settlement ownership and shutdown) is described in [runtime lifetime](runtime-lifetime.md). The CLI's default command loads this configuration at startup and serves MCP over stdio, as described in [transport](transport.md).

`loadConfiguration(environment)` reads the explicit environment keys in the [configuration contract](implementation-contracts.md#startup-configuration). It snapshots their values before filesystem work, resolves directory symlinks, deduplicates resolved upload roots and returns a frozen configuration with frozen roots and limits. It does not read `.env`, discover directories from the working directory or make network requests. An empty upload-root array is valid.

Instance URLs retain installation subpaths. The parser rejects embedded user information, query/fragment delimiters, whitespace, control characters, backslashes and unsupported schemes. HTTP requires the literal `TESTRAIL_ALLOW_INSECURE=true`. Email validation uses the driver's exported configuration schema. Credentials are preserved as supplied; empty or whitespace-only required values fail. Booleans accept only the literal strings `true` and `false`.

Upload roots must be absolute existing directories. Windows paths must identify a drive or UNC share; a path rooted on the current drive is rejected. The download directory must additionally pass write and traversal access checks and an exclusive one-byte write probe, which is closed and removed immediately. The probe verifies Windows ACLs that Node's access check alone does not evaluate. Failure reports only the configuration key. A failed removal can leave a tiny `.testrail-mcp-write-check-*` probe; startup fails in that case. These startup checks do not replace F07's checks when opening individual files: permissions and paths can change after startup.

Limits use the exact defaults and ceilings in the [budget table](implementation-contracts.md#runtime-budgets-and-lifetime). The limits object rejects unknown keys, nonnumeric values, nonpositive values, fractions and unsafe integers. The effective `max_all_bytes` must not exceed `max_data_bytes`, including when defaults are used. If lowering `max_data_bytes` below 1 MiB, explicitly lower `max_all_bytes` too; the parser never clamps either value. Fixed watchdog, shutdown, binary-concurrency and error-size budgets cannot be overridden through the environment.

`driverOptions(configuration)` maps only the approved settings to the public driver configuration. It disables caching and driver process handlers, sets request/body timeouts to 15 seconds, allows three driver retries, sets the rate budget to 100 requests per minute and applies JSON/binary response limits. `createConfiguredDriver(configuration)` constructs one client per call using those settings. The composition root, `startServer`, calls it once per process and owns destruction; `tests/transport/composition.test.ts` shows two protocol consumers sharing that one client and one budget. Its optional second argument, the driver's `fetch` and `dnsLookup`, is a test-only seam reached only through `startServer`'s options, which the CLI never sets. Every TestRail request connects directly, through a dispatcher the driver pins to the DNS answers its private-host guard approved (driver 9.0.0): global proxy and agent settings, `HTTP_PROXY`/`HTTPS_PROXY` with `NODE_USE_ENV_PROXY`, and a global Undici dispatcher are not used, and the server injects no transport, so an instance reachable only through a proxy cannot be used. `NODE_EXTRA_CA_CERTS`, set before the process starts, still adds trust for a private certificate authority. An insecure or private-host opt-in emits the driver's own warning twice during startup, once for the configuration probe below and once for the process client: the probe is a real client, and the driver warns from its constructor.

The driver's public constructor owns literal-host policy; its per-request network guards own DNS policy. That constructor policy is not exported, so `loadConfiguration` applies it through `assertDriverConfiguration(configuration)` before returning: no caller can hold a configuration that skipped the private-host and protocol rules. The probe client registers no process handlers and issues no request. It is destroyed at once, which zeroes its credential and removes it from the driver's process-wide set of live clients, so it does not remain a second credential identity. Before this was fixed, the probe was dropped without being destroyed and stayed in that set, credential included, for the life of the process.

Driver rejections are attributed structurally by re-running the driver's exported configuration schema, never by reading its thrown message, which embeds the configured host. A rejection naming an operator-settable field maps to that field's environment key; a schema-clean rejection is the URL network policy and maps to `TESTRAIL_BASE_URL`; a rejection of a transport setting this adapter fixes raises `DriverSettingsError` rather than naming a key the operator cannot correct. Configuration failures report `Invalid configuration: KEY.` with no source error attached. Unexpected internal errors propagate to the CLI's startup boundary in `src/cli.ts`. It reports a configuration failure by its key, which `tests/cli.test.ts` checks. It reports any other failure as the fixed `Unable to start the server.`; no test reaches that path yet. Configuration objects contain credentials and must never be logged.

The exact dependency is the qualified `@dichovsky/testrail-api-client@9.0.0`, whose installed-artifact checks are recorded in [driver qualification](driver-qualification.md). CLI startup and shutdown are integrated and tested; [transport](transport.md) describes the suites that drive the executable. [Runtime lifetime](runtime-lifetime.md) lists the suites for admission and settlement ownership.
