# Writing guide

This guide gives the rules for repository prose. It applies to new text and to each change of existing text.

## Standard and verification level

The target standard is [ASD-STE100 Simplified Technical English, Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf). The rewrite of 2026-11 is an **STE-principles rewrite**. It applies only the rules in [Core rules](#core-rules), without the specification text. No one checked the words against the ASD-STE100 dictionary. Thus, this repository does not claim that a word is approved or that a document is compliant with ASD-STE100.

If you check a document against a licensed copy of the dictionary, record the edition and the documents that you checked in this section.

## Scope

These files follow this guide:

- `README.md`, `CONTEXT.md`, `src/README.md` and `proxmox/README.md`;
- the top-level `docs/*.md` files, except `docs/operation-reference.md`.

These files are excepted. Do not rewrite them for style:

| Path | Reason |
| --- | --- |
| `CHANGELOG.md` | Historical record of releases |
| `LICENSE` | Legal text |
| `docs/adr/*` | Decision records. Each one records a decision at the time it was made |
| `docs/issues/*` | Issue specifications that GitHub issues link to |
| `docs/evidence/**` | Recorded evidence |
| `security_best_practices_report.md` | Dated review |
| `docs/operation-reference.md` | Generated by `npm run registry:generate` from the endpoint definitions. Do not edit it by hand |
| Runtime strings: tool descriptions, error messages, CLI output, log messages | Clients and their models read these strings. Tests assert many of them, and `docs/operation-reference.md` is generated from the tool descriptions. Change them only for a behavior change, with its tests |

## Core rules

Sentences:

- Write a maximum of 20 words in a procedural sentence. Write a maximum of 25 words in a descriptive sentence.
- Give each paragraph one topic. Write a maximum of 6 sentences in a paragraph.
- Use the active voice in procedures. Use the active voice as much as possible in other text.
- Keep the articles ("the", "a"). Do not use a telegraphic style.
- Do not use idioms. Do not use a phrasal verb if a single verb has the same meaning.
- Do not use "it", "this" or "that" without a clear noun to refer to.

Instructions:

- Write instructions in the imperative.
- Write one instruction in each sentence, unless the actions occur at the same time.
- Put instructions separate from descriptive text.
- Use vertical lists for sequences, conditions and options.
- Put the condition before the related instruction.

Warnings and cautions:

- Start with a short, clear command. Then give the reason.
- Do not weaken or remove a hazard.

Words:

- Use one word for one meaning, and one word for one concept. Do not use synonyms for variety.
- Use the terms in the [terminology table](#terminology).
- Keep the RFC 2119 keywords (MUST, SHOULD, MAY) exactly where they occur.
- Use US spelling (for example, "behavior") in new or rewritten sentences.

## What a rewrite must keep

A rewrite changes the words, not the meaning. Keep these items:

- requirements, prerequisites, warnings, limitations and exceptions;
- the difference between mandatory, recommended and optional;
- conditions, negations, quantities, units, limits, defaults and the order of steps;
- headings, because links use their anchors;
- links, anchors and cross-references;
- code spans, fenced code blocks and their behavior;
- identifiers, API fields, commands, flags, environment variables, configuration keys, file paths and protocol values;
- dates, commit references, version numbers and recorded findings;
- the text inside prompts that a person pastes into a client, because the scenarios use that exact text.

Some tests read the documents and assert exact phrases or table rows. Before you edit a document, find the tests that read it (`grep -rn '<file name>' tests`). Keep each asserted phrase and table row exactly as it is.

If the meaning of a sentence is ambiguous, find the answer in the code and the tests. If you cannot find it, keep the original sentence.

## Exceptions

- Headings stay as they are, because GitHub creates link anchors from them and other documents link to those anchors.
- Table rows that a test asserts stay as they are.
- The prompts in the client runbook stay as they are, because the client scenarios use the exact text.
- Some table cells contain more than one sentence, because a Markdown table cell cannot contain a vertical list. Some cells are lists of nouns, which stay as they are.
- Quoted text stays as it is: test titles, TestRail messages and the driver's match phrases. Some sentences that contain a quote are longer than the limit.
- "cancelled" keeps its British spelling, because the error code `CANCELLED` and the MCP notification `notifications/cancelled` use it.
- Some terms stay as they are in a sentence that mirrors a runtime string, for example "MCP host clients" in `docs/coverage-reports.md`, which repeats the statement that the coverage report writes.
- "certify" is used for the Node versions that CI tests. It is a different concept from "qualify".
- "SDK" means the MCP SDK (`@modelcontextprotocol/server` and `@modelcontextprotocol/client`), never the driver.
- "chunk" means a part of a file that is copied, not a page.
- "desktop app" and "the app" can name a desktop host in a procedure.
- Older sentences that were not rewritten can keep British spelling (for example "behaviour" or "licence"). Use US spelling when you rewrite such a sentence.

## Validation

Run this command after a change to a document:

```sh
npm run check
```

The command builds the package and then runs all checks. These checks include the tests that read the documents, and `npm run registry:check`, which fails if `docs/operation-reference.md` does not match the registry.

The repository has no Markdown linter, formatter or link checker. Thus, review the links and anchors in a changed document yourself.

## Limits of automated checks

The tests check only the phrases, table rows and values that they assert. They do not check the meaning of the prose. A sentence-length count supports a review, but it does not prove that the text follows ASD-STE100. Thus, review each change in context, and compare it with the original text for each item in [What a rewrite must keep](#what-a-rewrite-must-keep).
