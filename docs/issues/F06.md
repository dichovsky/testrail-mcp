## Outcome

Expose honest pagination for all 24 helper-backed lists with a single endpoint tool per list.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

Architecture: [accepted design](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/architecture.md). Exact engineering contract: [implementation contracts](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-contracts.md). [Endpoint inventory](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/operation-inventory.json).

## Dependencies

- [F05: Implement preserved results, per-call warnings and truthful errors](https://github.com/dichovsky/testrail-mcp/issues/6)

Tracking epic: [full TestRail MCP release](https://github.com/dichovsky/testrail-mcp/issues/1).

## Scope

- Provide the shared binding adapter for the 18 controlled list helpers, default limit 50/offset 0 and supported maximum 250; provide their all-mode binding to public getAll helpers preserving filters. The T-family issues register actual endpoint tools; this foundation item does not wait for those dependents.
- Implement strict _mcp discriminated page/all controls and camelCase helper mapping. Reject query.limit/offset in all mode; reject aggregate-only controls in page mode; apply per-call limits only within server maxima.
- For variables, datasets, shared-step history, roles, groups and case statuses expose initial page plus bounded all only; reject manual page size/start/offset and invented cursors.
- Implement pagination wrapper fields/source/has_more/next_action and validated next_offset only when controllable. Keep available driver metadata under pagination.driver. Implement the contracts' metadata-only URL/query/path continuation parser: collect canonical offset/limit, reject duplicates across forms, validate advancing/non-overlapping offsets, discard host/path as fetch authority and preserve caller filters. The driver does not publicly export its parser; do not use a private import or add a fetch loop.
- Default all bounds: 1,000 items, 20 pages, 1 MiB, 45 seconds. Driver limit failure yields PAGINATION_LIMIT and safe progress/reason, no partial aggregate; final output also passes F05 limits.

## Progress — 2026-09-17

Implemented page defaults, page/aggregate metadata and aggregate control mapping in `src/contracts/pagination.ts`. Notes in [pagination](../pagination.md).

- One page of 50 by default, maximum 250; aggregation is opt-in and maps to the public helper bounds, defaulting to the configured maxima.
- Next links are validated into caller-controllable numbers only. Controls are read from the query and from the path, because the real `_links.next` carries no `?` at all and lands entirely in `pathname`; a control repeated across both is rejected rather than preferred.
- A continuation must carry exactly one canonical offset, at most one limit within range, and must strictly advance past what the page returned, since replaying or overlapping would duplicate items silently.
- `returned` comes from the items present; driver `size` is preserved separately. When more data exists but no continuation validates, `next_action` is `all` rather than an invented cursor (since #44 it is `none`: the driver's aggregate refuses every link that fails this validation). Response-driven lists never offer manual paging.
- Mutation-checked. A fourth mutation that did not fail showed the hand-rolled link splitter was reimplementing `URLSearchParams`, which now does the work.

Still open on this issue: wiring these into registered list tools needs the catalog entries from T01-T12 and the registration path from F08.


## Progress — 2026-09-27 (acceptance audit)

"Still open" above is superseded: T01–T12 registered all 24 list tools and F08 serves them. This audit maps each acceptance item to the code and tests that hold it. Four read-only reviewers each took one item, broke it into atomic claims, and mutation-checked the tests on `main`. No behaviour needed fixing. Nineteen mutations passed every test, and review found ten more that passed earlier versions of these tests. Each now fails at least one test; the PR lists the counts.

**Tests added.**
- Empty pages: terminal, still linking on, and linking back to where they are, in page metadata and through a tool.
- A `next_offset` taken from the link rather than computed.
- The reported `start_offset` through a tool.
- Each of `max_items`, `max_pages` and `max_bytes` set exactly at what the list needs.
- A single last page that already passes a bound.
- The byte stop before another page.
- A malformed or non-advancing continuation through a tool.
- A link naming another endpoint, filter or host, followed only for its offset.
- The result budget in all mode.
- Progress counts exactly as the driver supplies them.
- Every aggregate-only control refused in page mode.
- The paging sentence in each description, and every paging control refused on an unpaged tool.
- No snapshot claim.
- No private driver import.

**One exception to item 4, recorded rather than changed.** The driver reads a bare-array reply on any list as its last page, because a bare array carries no continuation. So the aggregate stops there and reports `complete: true`. TestRail documents three lists that way:
- `get_attachments_for_plan` and `get_attachments_for_run`. Their descriptions warn about it (`src/operations/families/t12.ts:39`), and `tests/families/t12.test.ts:474` pins it.
- `get_case_statuses`. TestRail's reference contradicts itself here (`src/operations/families/t10.ts:189`), and the description gives no warning. `tests/families/t10.test.ts:185` reads the bare array as the whole list.

On any other list, a bare array would only come from an older TestRail (best effort). Whether TestRail ever returns a bare array with more behind it needs a live instance (R03).
