## Outcome

Define a single typed registration system for exactly 133 endpoint tools without losing supported parameters.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

## Scope

- Define registry metadata for route/method/token/name, family, public driver binding, input/outer/advisory schemas, explicit argument map, paging/file capabilities, TestRail mutation classification and MCP effects (including local filesystem effects). Family issues populate entries.
- Use top-level REST path names, strict query using REST spelling, body for JSON writes, file_path/optional filename/content_type for multipart, and _mcp only on supported lists. Explicit maps convert driver option names; preserve documented array/scalar serialization.
- Reuse exported Zod payload schemas, supplement runtime constraints and enforce unknown ordinary-field rejection while preserving supported flat custom_* and documented open-object payloads. Preserve omitted versus null and valid sentinel values.
- Create a reviewed independent per-endpoint parameter manifest and fixture format from TestRail/driver sources: requiredness, valid domains/unions, driver argument location, body/query serialization, outer result shape and representative invalid values.
- Generate MCP JSON Schemas, concise descriptions and reference docs. All tools enabled by default; no write unlock or confirmation parameter. Review effects per operation, especially report GETs and persistent attachment downloads. Keep remote mutation/retry policy separate from MCP hints.

## Acceptance and verification

- [x] Registry types prevent duplicate tool names and unsupported binding shapes; build-time parity identifies exact missing/extra routes and bindings, not just a total count.
- [x] Runtime and generated JSON Schema agree on path/query/body/file inputs, including UUID plan entries, numeric/UUID attachment IDs, refs arrays, custom fields, sentinel 0/null and unknown-key rejection.
- [x] Every parameter in the reviewed manifest has a mapping/validation test requirement; expectations are independent of registry generation. Per-family issues complete all entries before R01.
- [x] Descriptions are under 2 KiB and annotations describe real effects; no host allow/deny setting is changed and no dispatcher/helper tools enlarge the catalog.

## Implementation and verification

The F04 branch implements typed public driver calls, strict schema helpers, operation metadata/effects, registry parity, generated references and independent parameter fixtures. The local full check passes 80 tests, typecheck, lint, generated-reference verification and packed installation. A fresh independent review found and verified fixes for schema stripping/type loss, fixture format gaps and per-mode coverage checks; no findings remain.

Five representative manifests contain two complete input reviews and three explicitly partial reviews; 128 endpoints still need manifests. The production catalog has zero endpoint implementations. T01–T12 must populate all 133 registrations and finish their independent parameter fixtures; F08 still owns MCP serving. The registered-entry gate requires complete independent fixtures, matching per-mode argument targets, and runtime/JSON Schema acceptance checks for every added entry. Full-catalog parity remains an explicit failing gate until all families exist.

The linked implementation PR closes this issue on merge. It runs the six Node 22/24 × Linux/macOS/Windows checks. F01 remains open pending publication and qualification of the fixed driver; F04 does not change the development dependency or claim runtime/release readiness.
