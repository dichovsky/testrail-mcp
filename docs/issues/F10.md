## Outcome

Make fixture provenance re-review auditable, not just assertable ([#31](https://github.com/dichovsky/testrail-mcp/issues/31)).

A parameter manifest records the driver commit it was reviewed against. Before this work, moving that pointer to a new driver release was indistinguishable from a rubber stamp: the audit checked only that `driver_commit` was 40 hexadecimal characters and that the manifest's source links pointed at it. Nothing recorded what had been compared, so a bump could not be told apart from a review.

This record was written when the issue closed, after the work, and summarises the issue rather than reproducing its body. The issue on GitHub is the authority for its original wording.

## Dependencies

None. Related: [#30 (F09)](https://github.com/dichovsky/testrail-mcp/issues/30).

## Scope

- Record each driver advance as data the audit checks: which commit a fixture was first reviewed against, each step from there to its current commit, and for each step every cited driver file with whether it changed.
- Check those claims against recorded hashes of the driver's releases rather than taking them on trust, and keep `npm run check` offline.
- PR [#74](https://github.com/dichovsky/testrail-mcp/pull/74) took the full design (a release ledger with git blob IDs and shipped-file hashes) rather than the issue's cheaper alternative.

## Acceptance and verification

- [x] A `driver_commit` bump that carries no evidence fails the audit.
- [x] The five manifests first written at driver 7.0.0 carry evidence for their advance to 7.2.0.
- [x] Evidence that calls a changed file unchanged is rejected.

## Progress — 2026-10-03 (closing)

**Already in place.** PR #74 (merged 2026-09-27) shipped the mechanism. A manifest's `review` carries `authored_commit` and, once `driver_commit` has moved off it, an `evidence` chain. [`tests/fixtures/driver-releases.json`](../../tests/fixtures/driver-releases.json) records, for each reviewed driver release, its tag commit, npm integrity, and each cited file's git blob ID and shipped-file SHA-256. The audit compares every changed-or-unchanged claim with those hashes. The installed release's entry is held to the installed package offline, historical entries are pinned by digest, and `scripts/audit-driver-ledger.mjs` re-checked everything against a driver clone and npm by hand. PR #74 said "Part of #31" and left the domain library out of scope, because the library had no driver bump to evidence yet.

**What changed here, and why.**

- **The domain library's driver citations were outside every gate.** [`tests/fixtures/domains.json`](../../tests/fixtures/domains.json) has its own review pointer and one driver citation per domain, 13 in all. Nothing checked them: a domain source moved to a 7.0.0 blob, to `blob/main`, or to a file that does not exist passed the whole suite. This is the same failure #31 describes, in the other fixture with a driver review pointer. It matters because a manifest's evidence covers only the files the manifest cites itself, and what a domain claims about the driver is stated only in the library. Today 103 of the 117 manifests that use `domain_ref` reference a domain whose driver file they do not cite: `src/validation.ts` in all 103, and `src/modules/cases.ts` as well in 14. At the next bump nothing would have made anyone re-review the domains those 103 manifests rely on. The manifests that cite those two files directly (12 each) would name them in their own evidence, but that covers their own claims, not the library's.
  - The library's `review` now carries `authored_commit` (set to `cc7751c`, where the library was first written in `a6a431e`) and an optional `evidence` chain. The evidence chain uses the same schema as the manifests', now shared as `provenanceEvidenceSchema` in `tests/contracts/driver-releases.ts`.
  - `auditDomainProvenance` in `tests/contracts/parameter-manifest.ts` holds the library to the ledger. It requires every domain's source to be a driver blob URL pinned at the library's `driver_commit`, then runs the manifests' own `auditProvenance` over the library's citations. `auditProvenance` now takes a structural subject (a review and a list of sources). This is a type-only change: its body and every message are unchanged. The per-domain rule is stricter than a manifest's, which needs only one pinned driver source among several. Each domain has exactly one source and is authored from driver code, so a domain whose only source is other documentation is refused. Messages name the domain, because source IDs repeat across domains.
  - `tests/domains.test.ts` no longer hard-codes `7.2.0` and its commit. It requires the library's `driver_version` to equal the installed driver's, and pins `authored_commit`, as the manifests' are pinned.
- **The ledger audit now runs in its own workflow** (owner decision). [`.github/workflows/driver-ledger.yml`](../../.github/workflows/driver-ledger.yml) runs `scripts/audit-driver-ledger.mjs` on `ubuntu-latest` against a `--filter=blob:none --no-checkout` clone of the driver. It runs on a pull request or a push to `main` that changes the ledger or the script, and can be started by hand. It holds `contents: read` only, pins the same action commits as `ci.yml`, and installs nothing. The owner named two paths; the workflow file itself is a third, so that an edit to the workflow is exercised when it is made rather than at the next ledger change. This is the only check that compares the recorded git blob IDs with the driver's git history. That matters most at the next bump: the new installed entry's blob IDs cannot be checked offline, and the ledger maps `src/x.ts` only to `dist/x.js`, so a type-only source change could otherwise hide behind a fabricated blob ID. Neither `ci.yml`, with its three-platform matrix, nor `npm test` runs the script or clones the driver.
- **The script now checks that each release's commit is its release tag.** The guide says the ledger records each release's tag commit, but the script judged blob IDs at whatever `commit` said and fetched the tarball by `version`, and nothing tied the two together. It now resolves `refs/tags/release/<version>^{commit}` in the clone and reports `<version>: commit <short> is not tag release/<version> (<tag commit or missing>)` on a mismatch.
- [`docs/parameter-manifest.md`](../parameter-manifest.md), "Driver provenance evidence": the ledger covers files the library cites; a new paragraph describes the library's review and its stricter rule; the script's tag check and the workflow are described; and advancing the driver now includes re-reviewing the library. "Shared parameter domains" says the probes prove values while the provenance rule holds citations.

**Limits that remain.**

- `authored_commit`, for the manifests and the library alike, is declared and pinned by a test. The offline gate has no history to derive it from.
- Historical ledger entries are pinned by digest offline. Only the networked script, now run by the workflow, compares them with the driver's history and npm.
- The installed release's git blob IDs cannot be recomputed offline, because the package ships no sources.
- Declaration files (`.d.ts`) are not in the ledger. A type-only source change that leaves `dist/*.js` identical shows up only as a blob change, which only the networked check sees.
- The workflow depends on github.com and registry.npmjs.org being reachable. The path filter limits that exposure to edits of what it checks.
- The test that keeps the driver out of CI, the release workflow and npm's scripts reads their text for the driver's repository name. A clone whose repository name is assembled from variables would pass it.
- The library's `review.reviewed_on` is still 2026-09-18. 10 of its 13 domains were added on 2026-09-19 and 2026-09-20, and the file was last edited on 2026-09-27. It is left as recorded, because this batch did not re-review the domains' content. An evidence step must be dated no later than the library's `reviewed_on`, so a step dated when the next bump is actually reviewed will fall after 2026-09-18 and that bump will need to move `reviewed_on` too. The audit does not check that the dates are honest.

**Not done here.**

- `docs/operation-inventory.json`'s `driver_source_commit` (`89f636e2`), and the `89f636e2` links in the planning and research documents, have no evidence gate. They are planning citations, not fixture review pointers, so they are outside #31. Nothing checks them: registry parity (`npm run registry:check`) holds only the inventory's endpoint identities. Nothing is delegated for them.
- Nothing in this issue needs a live TestRail instance, an MCP client or Windows, so nothing is delegated to R02, R03 or a Windows-only check.
- F10 is not added to `docs/implementation-items.json` or `docs/issues/EPIC.md`, following F09's precedent.
