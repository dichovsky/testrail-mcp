## Outcome

Demonstrate complete 133-operation adapter coverage with independent tests before client and live qualification.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

## Scope

- Compare the executable registry and generated catalog with pinned inventory method+route+name+binding identities; fail missing/extra/duplicate mappings or unimplemented parameter manifest entries.
- Run all 133 real-driver fixture contracts plus negative/union cases for every supported parameter. Inspect the serialized request independently of the registry mapping; include custom fields, sentinel/null, UUIDs and bulk shapes.
- Integrate legacy/current packaged stdio tests, output-schema/text parity, all 24 paging helpers, warning isolation, malformed success, unknown writes, caps, soft cancellation, capacity retention after both adapter and driver-internal deadlines, deferred DNS/fetch/body settlement, file containment and persistence.
- Add regression tests for deliberately mutated fixture/registry samples: omitted endpoint, wrong path ID, lost optional query/body parameter, permissive unknown input, duplicate binding and false helper support must fail.
- Publish sanitized machine-readable coverage/parameter reports and fixture evidence as CI artifacts with exact package/driver versions.

## Acceptance and verification

- [ ] All 133 operations, 28 resources, 12 families and 24 page/all bindings are accounted for with independent passing assertions; every parameter-manifest row has coverage, not only every name.
- [ ] CI passes on Node 22/24 across Linux/macOS/Windows; packed executable protocol checks pass for both eras and stdout is clean.
- [ ] Mutation tests prove coverage checks catch meaningful omissions; repeated identical GET drift warnings remain correct under concurrency, and report generation policy tests use the fixed published driver.
- [ ] Reports distinguish offline fixture coverage from live/client results; no real TestRail credentials or user directories are needed for the deterministic suite.

## Progress — 2026-09-26

**Registry and fixture regression gates.** `tests/regression-gates.test.ts` runs over the production registry and the authored manifests, not synthetic samples.

- It accounts for the contract's 133 operations, 28 resources, 12 families and 24 page/all pairs. It holds the inventory's declared totals to its own rows key for key, and matches the registry against the inventory per family (each family holding exactly its own tools, each tool under the family that owns its resource) and per page/all helper pair, with 48 distinct helpers.
- It serves the full catalog to a legacy and a 2026-07-28 client over an in-memory transport. Both see exactly the 133 inventory names, identical on repeated discovery and with no TestRail request, and the same catalog as each other.
- It breaks real registrations and manifests and runs the owning gate over each: an omitted endpoint, a wrong path ID, a dropped query filter, a dropped body field, a permissive input schema, two tools on one driver method, a wrong HTTP method or route, helpers claimed by a list that has none, a manifest that loses every fixture for a parameter, and a fixture promising a path the registration does not send. Each test also runs its gate on the unbroken sample, which must pass, so a gate that refuses everything cannot satisfy it.

Before this, removing `testrail_get_project` from the catalog and regenerating the reference left every test and CI step green. `npm run registry:check` now runs in full-catalog mode and fails on a missing endpoint. The reverse gate, a manifest with no registration, is new. The production fixture runner moved to `tests/contracts/fixture-runner.ts` so these tests drive broken registrations through the same code.

**Protocol checks against the packaged executable.** `npm run test:package` installs the packed tarball into a clean directory and runs three MCP sessions against its executable, each with a TestRail stand-in on the loopback interface: a legacy `initialize` session, one pinned to 2026-07-28, and one the SDK's own stdio transport negotiates automatically, which must settle on the modern era. The negotiated era is read from each connection. Every session must list exactly the 133 inventory tools, twice identically, from the server rather than the client's cache, and without a TestRail request; serve `testrail_get_project` with one authenticated request; refuse a string ID as `INVALID_ARGUMENT` without a request; answer an unknown tool with the protocol's invalid-params error and keep serving; and, with Node's warnings silenced, write nothing to stderr but its JSON diagnostic events, starting with the startup event, free of the API key, the Basic credential, the email and the TestRail address. The two sessions over a recording transport also require every stdout line, a final unterminated one included, to be a complete JSON-RPC message and free of those values, the shutdown event, and the server to exit with code 0 within 10 seconds of stdin closing without being killed. Before this, the package check ran only `--help` and `--version`, and `lifecycle.test.ts`, which the transport notes described as driving the packaged executable, runs `dist/cli.js` in the legacy era only: an `initialize`, a malformed line, a ping and an unknown method, never listing or calling a tool.

Still to do under this issue: result-contract and paging integration through registered tools; runtime lifetime through registered tools; and the machine-readable coverage reports as CI artifacts.
