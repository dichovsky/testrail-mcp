## Progress — 2026-09-27

**Documentation that matches what ships.** The README now describes the implemented server:
- install from a packed checkout until the first npm release;
- every environment variable, required and optional;
- each configurable limit's default and ceiling;
- the request, response-wait and page budgets;
- results, errors, write outcomes and pagination, including the six lists that choose their own pages;
- file handling and retention, side effects, and soft cancellation.

The client guide's status line no longer says the server is unimplemented, and it now lists the optional variables.

`tests/docs.test.ts` holds both documents to the code:
- the README's variables equal the configuration contract's, with the same requiredness;
- a required variable's absence, or an optional one's unusable value, stops startup with that variable named;
- the variables the README names are exactly those the server reads;
- the limits table and its MiB figures, and the budgets, equal what the code enforces;
- every error code the README names is one the server defines, every write outcome it names is one the server returns, and it names all three;
- the six response-driven lists equal the inventory's, and the counts of paged lists and of those that take a page size match it;
- the Codex example parses as one TOML table, and the Claude Code and Copilot CLI examples as JSON; each launches the `testrail-mcp` executable, passes through exactly the required variables and sets a 120-second timeout;
- the Copilot CLI example, and not the Claude Code one, keeps `tools: ["*"]` and `deferTools: "auto"`;
- the guide's two variable tables hold exactly the required and the optional variables, and every check file its first verification stage names exists.

**A kit for running the client scenarios without a TestRail account.**
- **Stand-in.** `scripts/fixture-testrail.mjs` answers all 133 endpoints on the loopback interface, at every path the fixtures show the driver sending, with each endpoint's manifest reply. It prints synthetic credentials and logs requests without them. It can make every paged list hold several pages of a fixed length. Reserved path IDs produce:
  - 404, 400, 401 and 403 replies on every route with a path ID, in any of its numeric path IDs, and 500 on every write and report run;
  - usable drift and an unusable reply on the GET routes that return JSON;
  - a 20-second reply, which the driver's 15-second timeout ends, and slow pages that stop a complete read at its 45-second budget;
  - a large page and an oversized page on every paged list with a path ID, which `"all"` stops at its byte budget.

  Its request log marks a request the client gave up on, and a log that fails once it is serving stops it with an error.
- **Catalog helper.** `scripts/catalog-hash.mjs` prints the catalog an installed server lists in both protocol eras, with the revision each session negotiated. The C01 record needs it.
- **C03 corpus.** `tests/fixtures/clients/c03-corpus.json` holds one natural-language task per API resource. Each prompt states every expected value and names neither the tool nor an argument.
- **Evidence records.** `docs/evidence/clients/` holds one record per required surface, with all twelve scenarios `not_run`.

The tests:
- `tests/fixture-testrail.test.ts` starts the stand-in as a tester would and drives the production tool pipeline at it in-process, with the real driver over real HTTP. Every one of the 133 tools gets its fixture's reply, down to each item of a generated page and the bytes of a download. Each reserved ID produces its documented outcome on every route the guide gives it, in each numeric path ID; the two delay IDs run on the one route each names. Each row of the guide's table, its reply, routes and outcome, is checked against the test's own table. Every paged list spans its pages. The slow delays and page count are held against the driver's timeout and the 45-second budget.
- `tests/client-kit.test.ts` holds the corpus to the inventory and to each tool's input schema. It checks every record rule with a record that breaks it: a record of nothing run states nothing, not even a limitation or a note; a blocked surface says when, who, which client and why; a result needs its client, model, versions, provenance and evidence, and a pass its negotiated protocol. It refuses credentials, email addresses, local paths, variable values, key-like tokens and credentials in links in a record, and ties the guide's status table and expected catalog hash to the records and the registry.

No client has been run yet, so none of the acceptance items above is met.
