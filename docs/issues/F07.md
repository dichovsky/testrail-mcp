## Outcome

Make attachment and BDD file operations work within configured local directories with bounded size and explicit ownership.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

Architecture: [accepted design](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/architecture.md). Exact engineering contract: [implementation contracts](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-contracts.md). [Endpoint inventory](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/operation-inventory.json).

## Scope

- Implement resolved-root containment, regular-file and metadata validation, verified-handle bounded copying into private exclusive staging files, and streaming staged paths through the public driver interface.
- Require a .feature multipart filename for BDD. Validate attachment filename separately from content_type: slashes belong in media types, never filenames; reject control characters in both. Do not transfer an adapter-owned descriptor to the driver; close source handles exactly once and retain staged paths until the driver operation handle's settled signal, even when result has already rejected.
- Implement unique exclusive downloads in configured destination with measured bytes and {attachment_id,file_path,bytes}; one buffered binary download at a time, default 100 MiB limit shared with uploads.
- Remove failed/partial files, recover staging only with this server's marker, unique process directory and owner-PID evidence that the owner is definitely absent (uncertain/live/reused PIDs retain files), and preserve completed downloads across cancellation/delivery failures/restarts until user removal.
- Do not accept a caller download directory, invent filename/MIME metadata, embed binary base64 or claim protection against a malicious process running as the same user.

## Acceptance and verification

- [x] Disposable-directory tests cover traversal, symlink escapes, nonregular files, source replacement after staging, file growth/oversize, early DNS/driver failures and descriptor cleanup on all supported platforms.
- [x] Tests prove no overwrites under collisions/concurrency, exact byte counts, cleanup after write/close errors and retention of committed files across restart. Repeating a successful download creates two distinct retained files.
- [x] Cancellation/watchdog tests keep staged files and execution capacity until the driver operation handle's settled signal and adapter-owned file work complete, including internal aggregate/driver deadline rejection; live-process recovery never deletes another process's staging.
- [x] BDD and all multipart attachment bindings consume the same service; successful download paths are absolute and refer to the configured local directory.

## Progress — 2026-09-17

Implemented containment, staging and downloads in `src/files/`. Notes in [local files](../local-files.md).

- Containment resolves both the candidate and the roots and compares path components, so a symlink escape and a same-prefix sibling directory are both rejected. Missing, unreadable and out-of-root paths refuse identically so filesystem layout is not leaked.
- Staging copies through a handle opened at validation time, because forwarding a validated path leaves a window for the source to be replaced. The byte limit is enforced while copying, since a file can grow after it is measured. The driver receives a path, never an adapter-owned descriptor.
- Recovery deletes only directories carrying our marker whose recorded owner is provably absent; `EPERM`, an unreadable marker and a possibly reused PID all count as live. Completed downloads are never inspected.
- Downloads generate their own name, create exclusively, and return only after write and close. Partial output is removed on failure; committed files are retained even if delivery fails.
- Mutation-checked, and one mutation exposed a flawed test: the symlink-escape case had been passing because an unresolved macOS temporary root disagreed with the resolved candidate, not because the protection worked. The fixture now resolves its base.

- Security review found that opening the source could block indefinitely on a FIFO inside an allowed root, before the regular-file check could run, holding a libuv worker and exhausting the default threadpool after four calls. The source is now opened non-blocking. The accompanying test gap is closed too: the only non-regular case covered was a directory, which fails on its own through `EISDIR`, so the explicit guard could have been deleted unnoticed.

Still open on this issue: wiring staging retention to the runtime settlement signal, and the attachment tools themselves, need T12 and F08. The copy loop also needs a deadline there, since a slowly growing file that stays under the byte limit can hold a call slot; the invocation runtime already owns the response-wait budget and is the right place for it.

## Progress — 2026-10-03 (closing)

This closes F07; the pull request that carries it closes #8. The 2026-09-27 audit left three code gaps, and the owner settled the two open questions on 2026-10-03. Each code change below was mutation-checked. Tests are cited by name (`describe` > `it`), because line numbers drift.

**Staging now runs inside the call's slot.** Before, `executeToolCall` copied the file before `runtime.invoke`, so the copy was outside the four-slot limit, had no deadline and ignored cancellation. Uploads of slowly growing files could copy any number at once, a call refused as `BUSY` copied its file first and then deleted it, and a cancelled call kept copying. `executeToolCall` (`src/transport/tool-call.ts`) now stages inside the callback `runtime.invoke` tracks, so the runtime admits the call first, and the slot, the 60-second response watchdog and the caller's cancellation all cover the copy. `stageUpload` (`src/files/staging.ts`) takes a signal, checked before anything is opened and before each 64 KiB chunk; the pipeline aborts it when the call answers with an error, and it also follows the caller's cancellation. A copy that finishes after either is not sent. `dispatched` is now set after staging, immediately before the driver method, so a wait that ends during staging reports `write_outcome: "not_started"` truthfully. The catch no longer disposes a copy, because a call refused at admission has none; settlement cleanup is the only disposer. `src/runtime/invocation.ts` is unchanged. Two consequences are documented in [local files](../local-files.md): a filesystem call that never returns, such as a read on a hung network mount, holds its slot until it returns; and a server whose slots are all busy answers `BUSY` before it checks an upload's path, so a file that would be refused is reported as `BUSY` rather than `FILE_ACCESS_DENIED`.

**File identities are compared exactly.** The check that the opened handle and the path name the same file compared inode and device as JavaScript numbers. Node reports a 64-bit file ID as a double unless asked for BigInt. An NTFS file ID keeps a sequence number in its top 16 bits, so Windows IDs routinely exceed 2^53, and two IDs that differ only in their low bits round to the same number. On Windows, which has no `O_NOFOLLOW`, this check is the only defence after the open, and the audit's Windows claims rested on it. Staging now reads both stats with `{ bigint: true }` and compares them exactly.

**A removed copy no longer holds its bytes.** The driver streams the staged path through Node's `openAsBlob`. After a request body is abandoned part-way, that Blob keeps a descriptor on the copy until garbage collection, and an unlinked file keeps its blocks while any descriptor is open. On a memory-backed `/tmp` that is up to `max_file_bytes` of memory per abandoned upload. A probe that reads a Blob from `openAsBlob` part-way and cancels it, run on Linux with Node 22.22.2 and 24.21.0, found one descriptor still open after cancellation and after unlinking, and none after a forced collection or after a full read. A staged copy's disposer now empties the copy (`truncate` to 0) before removing it; with that, the same probe finds the lingering descriptor on a 0-byte deleted file. The staging area itself is still only removed at shutdown, never emptied, because an upload may still be reading its copy then.

**Windows, reclassified.** The audit marked "all supported platforms" as partly held because three cases are skipped on Windows.
- Open-file replacement: the fixture renames over an open file, which Windows refuses. The audit's "the open-file race cannot be staged there" overclaims: only that fixture cannot run there, not every replacement race. On Windows the identity check is exercised instead by "upload staging > refuses a final component swapped for a symlink before it is opened", where the open follows the link and the identity check refuses it, and by "upload staging > compares file identities exactly, even beyond 2^53", which runs on every platform. The new close-count case "upload staging > closes each handle exactly once on a final component swapped for a symlink" expects the source handle closed once after that refusal on Windows, and nothing opened where `O_NOFOLLOW` exists.
- FIFO: not applicable. A Windows named pipe lives only under `\\.\pipe\` and cannot sit inside a directory root.
- Permissions: owner decision D2 below.
