## Outcome

Release the complete server only when the agreed baseline and required clients have verified behavior.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

## Scope

- Prepare a dedicated disposable TestRail 10.7.0 environment/project with the licensed features, permission profiles and fixtures needed for all baseline endpoint families; map each operation to live evidence or a documented missing capability. *(The owner's 2026-10-03 decision, below, made a missing capability a documented limitation rather than a blocker.)*
- Run ordered create/read/update/list/close/delete lifecycle checks, bulk operations, BDD/shared steps, datasets/variables, plan configurations, metadata/admin, attachments and report generation. Use report templates configured for the test to control notification effects.
- Record API/license/permission/version limitations without hiding tools; older versions are best effort. Live evidence must distinguish supported baseline failure from unavailable test infrastructure.
- Qualify exact fixed published driver from F01, rerun deterministic/client gates for the final candidate, and produce package/version/lockfile/integrity/SBOM or dependency inventory, changelog and endpoint reference.
- Create a version-tagged GitHub Actions release workflow using npm trusted publishing where available, protected release environment and least-required token permissions. Publish only after the actual release is authorized under repository policy, then verify install and packaged stdio startup from the exact registry artifact.
- Document upgrade/rollback via exact npm versions and compatibility policy; do not delete previously downloaded attachments during upgrade or uninstall.

- [ ] README/configuration/reference docs match shipped names, budgets, side-effect annotations, files, errors and pagination limits. Publishing credentials are never stored in source or evidence.

## Progress — 2026-09-27

**The release pipeline, prepared but not yet run.** No release has been published, and none of the acceptance items below is met.
- `.github/workflows/release.yml` runs only for a `vX.Y.Z` tag, as five jobs, each with only the permission it needs:
  1. `verify` re-runs every check on Node 24 across Linux, macOS and Windows.
  2. `build` writes the notes, the tarball and a CycloneDX inventory of a clean production install.
  3. `publish`, alone in the protected `npm-release` environment and alone holding `id-token: write`, publishes that tarball once through npm trusted publishing, with provenance. It installs and runs no package code, and no npm token is stored.
  4. `verify-published` installs the version from npm, checks the served integrity and the provenance attestation, and drives the installed executable over MCP in both protocol eras.
  5. `release`, alone holding `contents: write`, creates the GitHub release.
- A re-run after a later failure recognises the published tarball by its integrity and completes the release.
- `scripts/release-notes.mjs` takes the notes from the tagged version's dated `CHANGELOG.md` section and refuses a tag that does not match `package.json`.
- `docs/release.md` holds the versioning and compatibility policy, the one-time GitHub and npm setup with both bootstrap routes, the release checklist, and how to upgrade, roll back and uninstall without touching downloads.
- `tests/release.test.ts` checks:
  - the workflow's trigger, each job's exact permissions and order, and the steps the jobs run, with every step, variable and command of the publish job;
  - the publish-once step, run against a stand-in npm, and the npm version gate, run with real versions;
  - that every action in every workflow is pinned to a commit;
  - the release notes, run through a symlinked path too, and that the version pull request can pass;
  - the registry checks, against a stubbed registry;
  - the published-package check, run on a local tarball;
  - the inventory, against the lockfile.

npm allows a trusted publisher only on a package that already exists, so the first version needs a one-time bootstrap; `docs/release.md` gives the two routes, and the owner chooses one before tagging 1.0.0.

**npm placeholder, 2026-10-02.** The owner took the placeholder route and published the deprecated `0.0.0-bootstrap.0` under the `bootstrap` tag. **The live qualification runner, run three times against a live instance.** `scripts/live-qualification.mjs` calls all 133 tools in an order that builds each entity before it is read, updated, closed or deleted. It records each tool as `pass`, `fail`, `blocked` (a missing licence or permission, or a prerequisite that was blocked or failed) or `not_run`, with the reason. It must not change existing data:
- it creates one qualification project and writes only inside it, to entities it created;
- a guard refuses, before sending, any write naming an ID the run did not create;
- writes outside the project (users, groups, a case field) need `--instance-writes`, for a disposable instance;
- reports need a template the operator names;
- each attachment is deleted itself, then the project, at the end or on the way out if the run stops early;
- after cleanup, the runner reads the project and each attachment back, and fails the run if TestRail still has any or cannot say.

The evidence carries statuses and codes only, and the runner refuses to write it if it contains the address, credentials or the signed-in user's address. `tests/live-qualification.test.ts` runs the whole plan offline against the fixture stand-in, with every tool passing, and covers the guard and each way a run can stop. `docs/live-qualification.md` is the operator guide.
