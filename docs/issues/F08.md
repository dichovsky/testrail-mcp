## Outcome

Serve the complete operation registry through the official stdio SDK for the required local clients.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

Architecture: [accepted design](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/architecture.md). Exact engineering contract: [implementation contracts](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-contracts.md). [Endpoint inventory](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/operation-inventory.json).

## Scope

- Compose the process runtime, registry and SDK with serveStdio(factory) from @modelcontextprotocol/server/stdio; keep default legacy support and one process-owned driver.
- Implement deterministic complete discovery, tool registration/schemas/annotations, input and result adapter hooks, cancellation state and host-lifecycle handling.
- Keep stdout protocol-only and use safe stderr diagnostics; malformed protocol/unknown tools remain protocol errors while API/business failures are tool errors.
- Keep transport code independent of endpoint logic. Add concise server instructions with essential cross-tool rules in the first 512 characters and total under 2 KiB. No remote HTTP service or duplicated resources/prompts in this release.

## Acceptance and verification

- [ ] Independent sessions exercise legacy initialize/initialized/tools-list/call and modern MCP 2026-07-28 discovery/calls against the packaged executable. Record negotiated behavior rather than inferring from SDK version.
- [ ] Repeated discovery is deterministic and has no TestRail network side effects; once families are populated it exposes exactly 133 tools with no helper or generic dispatcher tools.
- [ ] Protocol tests cover invalid input, unknown methods/tools, structured/text success/error outputs, client cancellation, stdin closure and signals without stdout contamination.
- [ ] Factory re-creation does not multiply driver credentials/rate budgets or prematurely dispose shared state.

Execution order and release gates: [implementation plan](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-plan.md). This issue describes work to implement and verify; it is not a record of completed implementation.

## Progress — 2026-09-18

Implemented the composition root, tool registration, the per-call pipeline and stderr diagnostics in `src/transport/`. Notes in [the transport documentation](../transport.md). The CLI now serves MCP over stdio; with an empty catalog it exposes zero tools until the families land.

- Configuration, driver and runtime are created once in `startServer` and closed over by the factory, because `serveStdio` pins one instance per connection and may call the factory again when an era falls back. A second instance therefore cannot mean a second credential or rate budget.
- Tools advertise the reviewed JSON Schema verbatim through a passthrough schema. Handing the SDK a Zod schema would re-emit it in another dialect, and letting the SDK validate would reject arguments with a bare error carrying no structured content, bypassing the adapter's taxonomy. Both are pinned by tests: swapping in the Zod schema fails two of them.
- `outputSchema` describes only the wrapper with `data` unconstrained, and the SDK skips output validation for error results, so advisory drift cannot become a transport failure by either route.
- Diagnostics are JSON lines on stderr carrying fixed codes, tool names, a correlation id, durations and counts only. Routing them to stdout fails the packaged lifecycle test.
- Shutdown is idempotent across stdin closure, `SIGINT` and `SIGTERM`.

Two behaviours are recorded rather than claimed, both covered by tests so a future SDK change surfaces here rather than in a release claim:

- The eras serialize an advertised schema's keys in a different order while carrying identical keys and values, so catalogs are compared structurally across eras and byte-for-byte only within one.
- A malformed line receives no reply. The SDK's stdio transport drops what it cannot parse without emitting `-32700` and without an error callback, and there is no id to answer. The connection keeps serving. R01 should record this rather than assert the contract's "malformed protocol messages as protocol errors" sentence unqualified.

Review found three faults in the call pipeline, all fixed here and each pinned by a mutation:

- A download identifier was coerced to `0` unless numeric, but TestRail accepts a UUID and the driver's own signature is `number | string`. Every UUID download would have carried a placeholder id, breaking the result contract's "original validated ID".
- A staged upload copy leaked whenever the runtime refused a call at admission, because `BUSY` and pre-dispatch cancellation are thrown before the slot that runs cleanup exists. The catch now disposes it.
- The pipeline read a nested `file` object, while the registry reserves the flat `file_path`, `filename` and `content_type`. No real upload would ever have been staged. The registry's layout check surfaced this while the leak test was being written.

Also called out by review and not fixed here: the "one server per connection" test asserts only that the factory ran at least once, which would not catch a mutant that rebuilt dependencies per call. The underlying claim was verified against the SDK source, but the test does not pin it; forcing an era fallback and asserting a construction counter would. Client cancellation reaching `ctx.mcpReq.signal` is likewise unproven by test.

Still open on this issue: the acceptance criteria that need a populated catalog — exactly 133 tools with no helper or dispatcher tools, and full-catalog discovery against the required clients — plus client cancellation evidence against real hosts, which belongs with R02.

## Progress — 2026-09-27 (acceptance audit)

"Still open" above is superseded: T01–T12 populated the catalog, so the 133-tool criteria can now be checked. The note that client cancellation is "unproven by test" is stale too. `tests/transport/cancellation.test.ts` fails when the handler's signal is not passed. This audit maps each acceptance item to the code and tests that hold it. Four read-only reviewers each took one item, broke it into atomic claims, and mutation-checked the tests on `main`, crediting the F03 audit (#76) where it already holds a claim.

**Behaviour fixed.** The server instructions' first 512 characters ended mid-sentence, before the rule that an `unknown` write may already be applied and must be checked before retrying. A host that truncates at 512 characters lost it. The opening paragraph is rewritten to 492 characters, ending at a sentence, and holds every rule that prevents harm, each asserted as a whole sentence. The rest follows it, and the whole stays under 2 KiB.

**Recorded, not changed.** Valid JSON that is not a valid JSON-RPC message gets no reply, even with an id. JSON-RPC 2.0 asks for `-32600`, but the SDK's stdio transport drops it and reports it through `onerror`. A test pins this behaviour, and `docs/transport.md` records it next to the malformed-line case.

**Held elsewhere.**
- The F03 audit (#76) holds one driver and one budget across two connections, sharing one shutdown, and signal handling.
- Proposals that would change `scripts/package-protocol.mjs` or `scripts/catalog-hash.mjs` are left to their owners. The vitest suites here hold the same claims instead.
