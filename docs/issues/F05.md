## Outcome

Return consistent usable results while preserving TestRail data and identifying uncertain mutation outcomes.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

Architecture: [accepted design](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/architecture.md). Exact engineering contract: [implementation contracts](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-contracts.md). [Endpoint inventory](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/operation-inventory.json).

## Dependencies

- [F03: Implement configuration, driver ownership and bounded invocation lifetime](https://github.com/dichovsky/testrail-mcp/issues/4)
- [F04: Build the operation registry, strict inputs and parameter manifest](https://github.com/dichovsky/testrail-mcp/issues/5)

Tracking epic: [full TestRail MCP release](https://github.com/dichovsky/testrail-mcp/issues/1).

## Scope

- Implement {data,pagination?,warnings?}, structuredContent plus identical JSON text, void-to-null after resolution, raw BDD strings and documented file/page projections. Keep arbitrary driver-returned fields/custom_* unchanged.
- Separate strict required outer/list/page validation from advisory entity validation performed independently for each caller. Use original returned values, not parsed/coerced schema output; coalesced GET joiners must each receive warnings.
- Implement the fixed error taxonomy and safe metadata allowlist in the contracts, correct subclass precedence, bounded SCHEMA_DRIFT warnings and sanitized stderr events.
- For TestRail mutations and report generation track not_started before invocation, unknown after ambiguous rejection/timeout/cancel, and acknowledged after the driver handle's result resolves followed by adapter processing failure; settled is a separate resource-lifetime signal. No implied rollback, atomic bulk result or unconditional write retry. Do not infer TestRail mutations from readOnlyHint alone; attachment downloads have local effects and do not receive a TestRail write_outcome.
- Measure serialized data and complete duplicated/escaped MCP result; defaults 1 MiB and 2.5 MiB, errors 16 KiB, overrides bounded by config. Reject overflow without silent truncation.

## Acceptance and verification

- [x] Fixtures prove field/value preservation, custom-field extension, valid empty BDD text, void/null and response previews. Usable field drift warns; malformed outer structures error.
- [x] Concurrent identical GETs with one coalesced fetch each receive SCHEMA_DRIFT; concurrent different operations do not share warnings. Throwing advisory hooks cannot break production calls.
- [x] Error tests cover pagination-before-validation/license-before-API, missing resource versus version, status 0/200 parse failure, lost write response, bulk indeterminate errors and oversized acknowledged writes.
- [x] Quote/backslash/Unicode-heavy data tests measure the complete output after text duplication; no secret/raw error body/path leaks to diagnostics. SDK error responses are tested independently of success output-schema validation.

## Progress — 2026-09-17

Implemented the success wrapper, advisory drift warnings and the error taxonomy in `src/contracts/results.ts`, `drift.ts` and `errors.ts`. Notes in [results and errors](../results-and-errors.md).

- `data` preserves the driver value unchanged, including unknown fields and flat `custom_*`; void resolves to `null`; raw text stays text including a valid empty string. The text block is exactly `JSON.stringify(wrapper)`.
- Both budgets are measured separately in UTF-8 bytes. The text block duplicates and escapes the payload, so quote-heavy data inside the `data` budget can still overflow the result budget. Overflow is reported, never truncated.
- Outer validation is strict; entity validation is advisory, per caller, and discards the parsed output so a stripping or defaulting schema cannot alter what the caller receives. Only a bounded count crosses the boundary.
- Subclass precedence is enforced, since `TestRailLicenseError` extends `TestRailApiError` and `TestRailPaginationError` extends `TestRailValidationError`. Bound reasons map to `PAGINATION_LIMIT`, structural ones to `INVALID_RESPONSE`. Status 0 and 200 both map to `INVALID_RESPONSE`.
- `write_outcome` distinguishes `not_started`, `unknown` and `acknowledged`, is never derived from MCP annotations or from the error code, and is absent on non-mutating calls. Review found that keying it off the code let a post-dispatch failure carrying a pre-dispatch code report that nothing was sent; it now follows only what the adapter observed, with `unknown` as the conservative fallback.
- No driver message, status text or response body is forwarded; a leak test asserts a host, API key and local path are all absent from the envelope.
- Invariants are mutation-checked: dropping the result budget, measuring code units, reordering the license subclass and downgrading `unknown` to `not_started` each fail a test.

Still open on this issue: pagination metadata construction belongs to F06, and stderr diagnostic events need the serving process from F08.

## Progress — 2026-10-03 (closing)

The PR that adds this section closes F05 (#6). The audit above left two gaps it named: no test held the five server lifecycle events to their values, and a rejected tool handler would send its raw error message. A second audit on `main` at 36f0b59 found more. The audit's table cited several test lines that had moved, its preservation row claimed a per-tool proof for unknown fields that no test gave through the driver, and two code comments claimed more about diagnostics than the code holds. Two error choices were also still open, and the owner decided both on 2026-10-03. This section records what changed, corrects the table above, and maps every acceptance item to the code and the tests, cited by name, that hold it.

**What changed, and why.**
- *Lifecycle diagnostics are held field by field.* `DiagnosticFields` fixes which keys an event may have, not what they carry, and other suites check these events only by name or by substring. A download-directory path added to `server_stopping` or `staging_recovered`, or an extra field on `server_started`, passed every other transport, CLI and result-contract test. The new test runs the composition root through one lifetime and requires exactly `staging_recovered` `{removed: 1}`, `server_started` `{tools: 133}`, two `transport_error` events, `server_stopping` and `server_stopped`, with no other field. No stderr write may carry a local path, the configured credentials or host, or the key, host or path in the reported errors' messages. A table keyed by every event code lists each event's fields, so a new event code does not typecheck until it is listed, and the test then requires it to be seen.
- *A rejected handler is answered within the taxonomy.* The SDK answers a handler that rejects with the raw error message as the tool result, with no code and no write outcome. `executeToolCall` is built never to reject, so this cannot happen today, but the code already guards other paths that cannot happen, and the contract forbids forwarding raw messages. The registered handler now catches a rejection and answers `INTERNAL_ERROR` with its fixed message. A write or report run gets `write_outcome: "unknown"`, since whether the driver was entered is not known there. The handler also logs one `tool_call` line. This was decided by that convention, not put to the owner.
- *`transport_error` logs only an identifier.* It logged `error.name`, which is whatever the thrower set. A name that is not a plain identifier, up to 64 characters, is now logged as `Error`. The `DiagnosticFields.code` comment said it was always a taxonomy code, but for `transport_error` it is a class name such as `ZodError`. The `logEvent` comment said paths are "never accepted here", which the type does not enforce. Both comments now say what holds, and name the tests that hold it. `docs/transport.md` now lists the class name, the one addition to the contract's diagnostic list.
- *Unknown fields are held through the real driver, on every object a swept call returns.* For a reply that matches its schema, the driver returns its own parsed output (`client-core.js`, `if (result.success) return { value: result.data, matched: true }`). So an unknown field reaches the caller only while every driver schema passes unknown keys through. The test with a coercing advisory schema does send an unknown key through the driver, but its reply fails the driver's project schema, so the driver handed back the raw body; it shows only that path. The sweep through every tool now adds a key no driver schema names to every object, nested ones included, in the reply and in the expected data. 133 of the 157 calls carry it into `data`; the other 24 return nothing that could keep it (22 void methods, whose reply the driver discards, the BDD text and the downloaded file). The five uploads' replies pass no driver schema, so for them it holds only that the adapter keeps the key. Making the driver's milestone, report-result, version or history-change schema strip unknown keys passes the earlier sweep but fails ten cases of this one. An earlier version of this change marked only objects that carry an `id` (122 calls) and missed the last three; review caught it. An upgrade re-records the release ledger's hashes, so the ledger cannot tell whether a new schema stopped passing unknown keys.
- *D1, decided: a driver timeout is `TIMEOUT`.* When the driver gives up waiting on a single request, it raises `408 Request timeout after Nms` for its header timeout and a status-0 `Body read timeout` for its body timeout. Neither status is one TestRail sent. They reached the caller as `UPSTREAM_ERROR` with `http_status: 408` and as `INVALID_RESPONSE`. Both are now `TIMEOUT`, with no `http_status`. A write's `write_outcome` stays `unknown`. A 408 that TestRail did send stays `UPSTREAM_ERROR` 408, unless the driver abandons its body at one of its own limits: a body that stalls is replaced by the driver's body timeout, so it is `TIMEOUT` with no status whatever status TestRail sent. Inside an aggregate, the timeouts the budget clipped are still the duration bound; an unclipped one is `TIMEOUT` too. `testrail_get_attachment`'s description said a body that did not arrive in time was `INVALID_RESPONSE`; it now says a reply whose headers or body do not arrive in time is `TIMEOUT`, and `docs/operation-reference.md` is regenerated. The R02 stand-in's slow ID 990020 now documents `TIMEOUT` with no `http_status`. The live-qualification runner still lists a write that timed out as possible residue: with no status, it is not a refusal. It also keeps listing one that got a real 408. The report-run and upload failure tables in t11 and t12 now pin each code as well as the write outcome, so a real 408 sent through the pinned driver is held end to end as `UPSTREAM_ERROR` 408. The driver's own timeout, a row of the upload table and a case of its own for a report run, is held as `TIMEOUT` with no status. t11 also sends each report run a 200, a 408 and a 500 whose body stalls, and a template read a 500 and a 429 that stall and a 500 over the driver's JSON limit: each is sent once and keeps no status, `TIMEOUT` for a stall and `INVALID_RESPONSE` for the size limit, although the driver retries that read after a complete 500. The F03 record of this decision (`docs/issues/F03.md`) is updated by the F03 work in the same PR, not by this change.
- *D2, decided: an unreachable TestRail keeps its codes, now stated.* A failed, empty or private-address lookup before a request is a driver validation error, and so `INTERNAL_ERROR`. A connection that fails before any response headers arrive is the driver's status-0 network error, and so `INVALID_RESPONSE`. Both carry `write_outcome: "unknown"` on a write. The taxonomy has no code for an unreachable TestRail, and a new code would change what clients receive. `docs/results-and-errors.md` now says exactly what each case reports, and the test comments that called the lookup case an open question now record the decision. It also says that with `TESTRAIL_ALLOW_PRIVATE_HOSTS` set the driver does no lookup of its own, so a name that does not resolve fails as the connection does. A connection that breaks after the headers is neither case, and the decision did not cover it, but the same section states what the pinned driver does with it: a break during an error body keeps TestRail's status and is classified by it, so a licence reply whose text is lost is a plain 403, and a break during a success body is `INTERNAL_ERROR`. Three new rows of the lost-write test pin this.
