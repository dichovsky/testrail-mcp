## Outcome

Run one credential-bound driver per stdio process with honest timeout/cancellation semantics and bounded work.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

## Scope

- Implement the exact environment and limits table in implementation-contracts.md, including required URL/email/key/upload roots/download directory, strict optional booleans, TESTRAIL_MCP_LIMITS, safe URL validation and no automatic .env loading.
- Adopt the exact published driver qualified by F01 in the package/lockfile. Use its per-operation `{ result, settled }` handle for every public method call; result supplies the value/error and settled supplies descendant cleanup evidence.
- Create one driver with `registerProcessHandlers: false`, caching disabled, 15-second request and body timeouts, `maxRetries: 3`, a rate budget of 100 requests per minute, configured JSON/binary caps; no separate MCP retry/cache layer.
- Admission defaults to 4 active calls, 1 binary download within that count, no unbounded queue; reject excess as BUSY before invocation. Shared process runtime must outlive individual SDK protocol instances.
- Implement a 60-second response-wait watchdog and call cancellation state. Before driver invocation cancel without dispatch; after invocation retain capacity, observe late completion and keep temporary resources until both the driver handle's settled signal and adapter file work finish. A driver aggregate deadline can reject result before DNS/fetch/body cleanup completes; never treat that rejection as settlement. The driver has no public per-call abort signal.
- Handle stdin closure/SIGINT/SIGTERM once: stop admission, drain up to 5 seconds, dispose driver and exit. Preserve committed downloads and record indeterminate writes without pretending shutdown rolls back work.
- Provide sanitized structured diagnostics on stderr and test-only fetch/DNS injection through the composition root, never via production tool arguments.

## Progress — 2026-09-17 (runtime admission and lifetime)

`src/runtime/invocation.ts` implements admission, capacity accounting, the response-wait watchdog, cancellation state and shutdown over the driver qualified by F01. Notes in [runtime lifetime](../runtime-lifetime.md).

- Capacity is released on the driver's `settled` signal plus adapter-owned cleanup, never on `result`. An aggregate rejecting at its own `maxDurationMs`, and the adapter watchdog, both reject while descendants are still running; releasing on either would let the next call start work the previous one has not finished.
- Admission decides before dispatch, so a refused call issues no upstream request. No queue: excess load is `BUSY`.
- Capacity counts owned invocation scopes, not network requests. The driver joins identical in-flight GETs with caching disabled, so four concurrent identical reads share one upstream request while holding four slots. Covered by test.
- Cancellation before dispatch starts nothing; after dispatch it stops adapter-side waiting but retains the slot until real settlement, and late results are observed rather than surfaced.
- Shutdown stops admission, drains up to the fixed window, and destroys the client exactly once so a second protocol consumer cannot tear down a shared credential.
- Central invariants are mutation-checked: releasing on `result`, ignoring cleanup, or permitting a second `destroy` each fail exactly one test.

- Slot release cannot fail: adapter cleanup is wrapped so a synchronously-thrown fault is observed rather than escaping as an unhandled rejection. Reverting to a `.catch` on the return value reproduces an unhandled rejection that fails the run while every test still passes.

Still open on this issue: CLI composition-root wiring, stdin/SIGINT/SIGTERM handling and sanitized stderr diagnostics, which need a process that actually serves — they land with F08. The DNS-deferral, multipart-cleanup and coalesced-ownership cases F01 left uncovered also belong to that work.

**What changed and why:**
- **A late result rejection now has one observer, and tests that see it go.** `invoke` in `src/runtime/invocation.ts` observed the driver's result twice: `Promise.race` subscribes to it synchronously, and a `void handle.result.catch(() => undefined)` in `finally` subscribed again. The second observer ran only after the race had answered, so it never covered the window between starting the operation and the race. It also masked the first: with it present, dropping `handle.result` from the race left the test that checked for an unhandled late rejection (`tests/transport/composition.test.ts` > the composition root > "records a write pending at shutdown as unknown, and stops cleanly when it fails during the drain") green. Only the timeouts from lost result delivery revealed the break. It is removed. A comment at the race now states the rule this leaves: the race is the result's only observer, so nothing between `trackOperation` and the race may yield or throw. The slot comment is corrected too. `settled` never rejects by the driver's contract, so the slot's `catch` guards adapter cleanup faults and a breach of that contract, not "a late descendant failure".
- **New runtime tests for a late rejection.** `tests/runtime-invocation.test.ts` > runtime admission and invocation > "observes a result that rejects after the watchdog has answered the caller", and the same for a cancellation. Each fails the request only after the caller has its `TIMEOUT` or `CANCELLED`. It requires the slot to stay held until that failure settles the operation, and no unhandled rejection. The "still held" check pauses first, as [runtime lifetime](../runtime-lifetime.md) requires of such checks, so a slot released one timer tick after the caller is answered fails it.
- **New runtime test for a result that rejects early.** `tests/runtime-invocation.test.ts` > runtime admission and invocation > "observes a result that rejects before the event loop turns: %s", for a call that rejects at once, the driver refusing an argument, and an injected DNS lookup that fails at once. Each result rejects before any request is sent, in the turn of the event loop that started the operation. The test requires the caller to get that error, no request, the slot released and no unhandled rejection. It holds the yield half of the rule that the comment at the race states. If `invoke` yielded to the event loop between `trackOperation` and the race, such a rejection would have no handler when Node checks for unhandled ones, and under Node's default that ends the server. The late-rejection tests above cannot see that break, because their request fails long after the race has subscribed.
- **The older "still held" checks in the same file pause too.** "reports TIMEOUT when the response wait expires but keeps the slot until settlement", "keeps the slot after a mid-flight cancellation and observes the late result" and "holds capacity after an aggregate rejects at its own deadline, until descendants settle" each checked the slot in the same tick the caller was answered, so a release deferred by one timer tick passed them. Each now pauses before it looks.

A real in-memory connection is served, and its close rejects after closing. Shutdown neither fails nor ends early: the drain still waits for the call in flight, then the driver is destroyed and `server_stopped` is logged. The rejection is stubbed, because the SDK's own close already absorbs the failures of the steps it awaits. The test therefore shows only that the composition root absorbs a rejecting close.

All four acceptance items are held by tests that discriminate.

**Delegated, and not F03 blockers:**
- **R02.** Observing two protocol consumers with real host clients is informational. F03's proof is in-process (composition), and the built CLI shows the shared runtime outliving a re-created server. It is complete without R02.
- **R03.** Nothing. Item 1's "no startup request" is the server's own behaviour, held offline and on the built CLI.
- **Windows only: signal tests.** The four `SIGINT`/`SIGTERM` tests run on POSIX only, because Node cannot deliver a catchable signal to a Windows child: `kill` terminates it outright. Stdin closure, the path stdio hosts use, runs on Windows in CI.
- **Windows only: slow-reader test.** "delivers every response before exiting" uses `sh`, so it is skipped on Windows. The ordering it guards is platform-independent, and the forced-exit tests above hold it on every OS. A `cmd.exe` variant could be checked only on a Windows CI runner. It is not an acceptance claim.
- **F05: single-call driver timeouts.** The owner decided on 2026-10-03 (F05 D1). When the driver itself gives up waiting on a single call, through its header timeout or its body timeout, the caller gets `TIMEOUT` with no `http_status`. `write_outcome` keeps its meaning, so a dispatched write is `unknown`. A real 408 reply from TestRail stays `UPSTREAM_ERROR` with `http_status: 408`. F05 implements this in the same pull request; F03 does not. Item 3 asks for the budgets to be told apart, and the timing tests do that by the instant each outcome arrives, whatever code it reports.

**Not delegated:**
- **Accepted and documented: a partial download at the forced exit.** A download write still under way when the drain gives up can be cut short by the exit that follows, leaving a partial file in the download directory. [Runtime lifetime](../runtime-lifetime.md) documents this window, and nothing is reported as downloaded in that case. It is a known residual risk, accepted at closure. No open issue tracks it: F07 closes in the same pull request and does not take it. Closing it would mean writing to a temporary name and renaming once the write completes.
- **Recorded only: the watchdog timer's `unref`.** Removing it passes the in-process runtime and transport suites, and no test pins it. The CLI's forced exit ends the process anyway, and no doc claims it. It is defensive only.

The pull request closes #4.
