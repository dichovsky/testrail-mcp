## Outcome

Run one credential-bound driver per stdio process with honest timeout/cancellation semantics and bounded work.

Implement within the accepted local-stdio design: one TestRail identity per process; one tool per endpoint; every operation enabled by default, including writes/admin/delete; no server-added confirmation. TestRail 10.7.0 is the full-coverage baseline; older versions are best effort.

Architecture: [accepted design](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/architecture.md). Exact engineering contract: [implementation contracts](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/implementation-contracts.md). [Endpoint inventory](https://github.com/dichovsky/testrail-mcp/blob/codex/testrail-mcp-plan/docs/operation-inventory.json).

## Scope

- Implement the exact environment and limits table in implementation-contracts.md, including required URL/email/key/upload roots/download directory, strict optional booleans, TESTRAIL_MCP_LIMITS, safe URL validation and no automatic .env loading.
- Adopt the exact published driver qualified by F01 in the package/lockfile. Use its per-operation `{ result, settled }` handle for every public method call; result supplies the value/error and settled supplies descendant cleanup evidence.
- Create one driver with `registerProcessHandlers: false`, caching disabled, 15-second request and body timeouts, `maxRetries: 3`, a rate budget of 100 requests per minute, configured JSON/binary caps; no separate MCP retry/cache layer.
- Admission defaults to 4 active calls, 1 binary download within that count, no unbounded queue; reject excess as BUSY before invocation. Shared process runtime must outlive individual SDK protocol instances.
- Implement a 60-second response-wait watchdog and call cancellation state. Before driver invocation cancel without dispatch; after invocation retain capacity, observe late completion and keep temporary resources until both the driver handle's settled signal and adapter file work finish. A driver aggregate deadline can reject result before DNS/fetch/body cleanup completes; never treat that rejection as settlement. The driver has no public per-call abort signal.
- Handle stdin closure/SIGINT/SIGTERM once: stop admission, drain up to 5 seconds, dispose driver and exit. Preserve committed downloads and record indeterminate writes without pretending shutdown rolls back work.
- Provide sanitized structured diagnostics on stderr and test-only fetch/DNS injection through the composition root, never via production tool arguments.

## Acceptance and verification

- [ ] Missing/invalid config fails before serving with key names only; no startup/discovery TestRail requests, credential output or stdout diagnostics. Private-host/insecure opt-ins map exactly to supported driver settings.
- [ ] Two protocol consumers in a process do not multiply driver identities or destroy shared state. Concurrent tests prove limits remain held after watchdog/cancel and after the driver's own aggregate deadline rejects result. Fill four scopes with deferred DNS/fetch/body cancellation, observe errors, and verify later calls return BUSY without new work until settled releases capacity. Include coalesced callers and delayed multipart cleanup; no unowned background growth across calls.
- [ ] Fake-clock/deferred-promise tests distinguish DNS wait, header/body timeout, retry delay, watchdog and aggregate budget. Document soft upstream cancellation rather than claiming a hard total deadline.
- [ ] Shutdown/restart tests prove destroy is called once, late failures are observed, pending writes are unknown and successful downloads survive. Busy/cancel-before-dispatch performs zero upstream calls.

## Progress — 2026-09-17 (runtime admission and lifetime)

`src/runtime/invocation.ts` implements admission, capacity accounting, the response-wait watchdog, cancellation state and shutdown over the driver qualified by F01. Notes in [runtime lifetime](../runtime-lifetime.md).

- Capacity is released on the driver's `settled` signal plus adapter-owned cleanup, never on `result`. An aggregate rejecting at its own `maxDurationMs`, and the adapter watchdog, both reject while descendants are still running; releasing on either would let the next call start work the previous one has not finished.
- Admission decides before dispatch, so a refused call issues no upstream request. No queue: excess load is `BUSY`.
- Capacity counts owned invocation scopes, not network requests. The driver joins identical in-flight GETs with caching disabled, so four concurrent identical reads share one upstream request while holding four slots. Covered by test.
- Cancellation before dispatch starts nothing; after dispatch it stops adapter-side waiting but retains the slot until real settlement, and late results are observed rather than surfaced.
- Shutdown stops admission, drains up to the fixed window, and destroys the client exactly once so a second protocol consumer cannot tear down a shared credential.
- Central invariants are mutation-checked: releasing on `result`, ignoring cleanup, or permitting a second `destroy` each fail exactly one test.

- Slot release cannot fail: adapter cleanup is wrapped so a synchronously-thrown fault is observed rather than escaping as an unhandled rejection. Reverting to a `.catch` on the return value reproduces an unhandled rejection that fails the run while every test still passes.

Still open on this issue: CLI composition-root wiring, stdin/SIGINT/SIGTERM handling and sanitized stderr diagnostics, which need a process that actually serves — they land with F08. The DNS-deferral, multipart-cleanup and coalesced-ownership cases F01 left uncovered also belong to that work.


## Progress — 2026-09-27 (acceptance audit)

The "Still open" paragraph above is superseded. F08 landed the composition root, signal handling and stderr diagnostics. The DNS-deferral, multipart-cleanup and coalesced-ownership cases are covered in `tests/runtime-lifetime.test.ts`. This audit maps every acceptance item to the code and tests that hold it on this branch. Four read-only reviewers broke each item into atomic claims and mutation-checked the existing tests. Where a claim was not truly held, it is fixed here.

**Behaviour fixed:**
- The process exited about 15 seconds after a signal when a request was hung upstream, not within the 5-second drain. The drain finished, but the driver's own 15-second request timer kept the process alive. The composition root now exits 250 ms after shutdown completes, on an unreferenced timer. Measured on the built CLI: 14.98 s before, 5.27 s after, for `SIGTERM`, `SIGINT` and a repeated `SIGTERM`.
- A second `SIGINT` or `SIGTERM` during the drain killed the process before the client was destroyed, because the handlers were registered with `once`. They now stay installed, and every caller shares one shutdown.
- The configuration probe client was never destroyed, so it stayed in the driver's process-wide client set with its credential. It is now destroyed at load.
- A write still pending at shutdown was recorded in the `tool_call` diagnostic only as `CANCELLED`, and that line is the only record once the connection has closed. The diagnostic now carries `write_outcome`.
- `startServer` gained the test-only fetch/DNS seam that the scope asks for, plus a stdio seam. The CLI never sets either.

**Tests added.** Before this change, twelve mutations the reviewers ran passed every vitest test. Each now fails at least one test; the PR lists which:
- serving before configuration loads;
- a TestRail request at startup;
- loading `.env`;
- echoing a configured value on stderr;
- a leaked watchdog timer, abort listener or retained slot;
- closing one connection shutting the runtime down;
- a driver and runtime per connection;
- zero retry backoff;
- a header timer that counts DNS time;
- shutdown not waiting for in-flight work;
- admission stopping only after the drain.
