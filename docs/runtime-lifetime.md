# Invocation lifetime

`src/runtime/invocation.ts` implements F03's admission, capacity accounting and shutdown over the driver qualified by F01. `src/transport/server.ts` (F08) creates one runtime per process and owns signal handling and stderr diagnostics.

## Capacity follows settlement, never the result

A slot is released when the driver's `settled` signal fires and any adapter-owned cleanup has finished — never when the caller's `result` settles. The two are genuinely different moments. An aggregate rejects at its own `maxDurationMs` while its fetch is still in flight, and the adapter's response-wait watchdog rejects independently of both. Releasing on `result` would let the next call begin work the previous one has not finished, which is precisely what the slot limit exists to prevent.

This is why F01 had to deliver `trackOperation`. Without an observable settlement signal there is no correct moment to release a slot, only a guess.

## Admission

Admission decides before anything is dispatched, so a refused call issues no upstream request at all. There is no queue: excess load is refused with `BUSY` rather than buffered. The default limit is four active tool executions with one binary download reserved inside that count; the download slot is taken before the request is issued.

Capacity counts **owned invocation scopes, not network requests**. The driver joins identical in-flight GETs even with caching disabled, so four concurrent identical reads can share one upstream request while still holding four slots. That is intended: the limit bounds what the adapter owns and must wait for, not how many sockets are open.

## Cancellation and the watchdog

Before dispatch, an aborted call starts no upstream request and returns `CANCELLED`. After dispatch, cancellation stops adapter-side waiting and discards the delivery, but it does not stop upstream work — the driver exposes no per-request abort — so the slot stays owned until real settlement, and a late result is observed rather than surfaced or left unhandled. The race that answers the caller subscribes to the driver's result in the same synchronous step that starts the operation, so a result that rejects after the watchdog or a cancellation has answered already has an observer. That race is its only observer, so nothing between starting the operation and the race may yield or throw. `tests/runtime-invocation.test.ts` ("observes a result that rejects after the watchdog has answered the caller", and the same for a cancellation) fails the request only after the caller has its answer, and requires no unhandled rejection and the slot held until that failure settles the operation.

The response-wait watchdog is a fixed 60 seconds. It bounds how long the adapter waits, and reports `TIMEOUT`. It does not abort upstream work and must never be described as a hard deadline.

The watchdog and the driver's aggregate deadline differ in one way that matters for capacity. The driver never learns that the adapter stopped waiting, so a DNS lookup answered after the watchdog still goes on to send its request, and the slot covers that request too. The aggregate deadline is the driver's own, so a lookup answered after it starts nothing. Either way the slot is held until the last of that work settles. The aggregate deadline reaches the caller as `PAGINATION_LIMIT` with reason `max_duration`, never as `TIMEOUT`; [results and errors](results-and-errors.md) explains the driver timeouts that are recognised as the same bound.

Slow or hung requests can therefore hold all four slots until they settle or the process restarts. Every further call is refused with `BUSY` and sends nothing in the meantime. This is the intended trade: the alternative is starting work the process cannot account for.

A slot release must never be able to fail. Adapter cleanup is declared as returning a promise, but a function written without `async` is still assignable and can throw before any promise exists, so a `.catch` on its return value would not see it. The whole release body is wrapped instead, so a cleanup fault is observed and discarded rather than escaping as an unhandled rejection, which under Node's default would terminate the server. `settled` never rejects by the driver's contract, so the wrapper guards cleanup faults and a breach of that contract, not late descendant failures. By the driver's `trackOperation` contract, its operation scope observes each piece of work it registers, including one that fails after the result has settled; the caller's race above observes a late rejection of the result itself. "survives an adapter cleanup that throws synchronously" in `tests/runtime-invocation.test.ts` requires the slot to be released and no unhandled rejection, so a fault that escapes fails that test by name rather than only failing the run.

## Shutdown

Shutdown stops admission first, then waits for outstanding work up to the fixed 5-second drain window, then destroys the client exactly once. The runtime is shared by every protocol consumer in the process, so shutdown is a process-wide act: whichever caller runs it ends admission for all of them. Calling it again does not destroy the client a second time, because destroy zeroes the shared credential. Closing one connection does not shut the runtime down; another connection keeps being served.

A call still stuck when the drain expires is abandoned: the adapter stops waiting for it without claiming the upstream work stopped. That work can still hold driver timers of its own, such as the 15-second request timeout, and they would keep the process alive after shutdown. The composition root therefore exits 250 ms after shutdown completes and stdout has flushed, on an unreferenced timer, so a process with nothing left running exits by itself first. Waiting for stdout matters: `process.exit` drops whatever stdout still holds, so a host that closed stdin and reads its last responses late would otherwise get a truncated line. A host that never reads keeps the process alive until it reads or closes the pipe. With a request hung upstream, the process exits about 5.3 seconds after stdin closes or `SIGINT` or `SIGTERM` arrives; 5.27 s was measured on the built CLI. Before that fix it stayed up until the driver's request timeout fired, about 15 seconds. The signal handlers stay installed for the whole shutdown, so a second signal during the drain waits for the first shutdown to finish instead of killing the process before the client is destroyed. No shutdown step can reject: a failure closing the connection, destroying the client or disposing staging is absorbed, so the stop is still logged and the exit still scheduled. A failed attempt to create the staging area is forgotten, so the next upload tries again instead of inheriting the failure. One window remains. A download writes its file inside the tracked operation, so the drain waits for the write, and a reply arriving after shutdown has closed the connection writes nothing. But a write already under way when the 5-second drain gives up can be cut short by the exit that follows, leaving a partial file in the download directory. Writing a whole file inside that last 250 ms window is unlikely, and nothing is reported as downloaded in that case.

## Verification

`tests/runtime-invocation.test.ts` drives the real driver with an injected fetch and DNS. Its central invariants were mutation-checked: releasing capacity on `result` instead of `settled`, ignoring adapter cleanup, and permitting a second `destroy` each fails at least one test here; releasing on `result` and ignoring cleanup also fail tests in the pipeline suites below. Its "still held" checks after the watchdog, a cancellation or an aggregate deadline pause before they look, so a slot released one timer tick after the caller is answered fails each of them. Its aggregates get a one-second budget and the tests count the requests before they check a slot or a cleanup, so a budget spent before dispatch shows up as a missing request.

`tests/runtime-lifetime.test.ts` proves the same rules through the production registrations and the tool pipeline, so a registration or pipeline stage that released capacity early would fail there even with the runtime intact. It fills all four slots with `testrail_get_project` held past the watchdog and with `testrail_get_projects` in all mode held past its own deadline, and shows the next call is `BUSY` with no new request until real settlement. It holds DNS past each deadline, a response body mid-read past the watchdog, and a body cancellation past the aggregate deadline; four identical reads joined into one request; and a `testrail_add_attachment_to_case` upload whose lookup outlives the watchdog, keeping its staged copy until the request has read it and settled. Upload staging holds its slot too: `tests/transport/upload-staging.test.ts` pauses a copy, fires the watchdog, and shows the slot held until the copy has stopped, with nothing sent. No test waits for the 60-second watchdog: it is fired by hand. The aggregate budget is a few milliseconds, or one second where an aggregate must reach the network first.

`tests/runtime-invocation.test.ts` also holds shutdown's order and what the runtime leaves behind. Admission is closed while the drain is still waiting, and the client is destroyed only after in-flight work settles. Across ten rounds of success, watchdog expiry, mid-flight cancellation and pre-dispatch refusal, every 60-second watchdog is cleared once its call answers, no abort listener stays on a caller's signal, and nothing is retained for shutdown to drain. `tests/runtime-lifetime.test.ts` fills all four slots with aggregates whose body cancellation is still pending, and `tests/transport/cancellation.test.ts` cancels four dispatched calls in both protocol eras. Both require the next call to be `BUSY` without a request until real settlement.

`tests/runtime-timing.test.ts` tells each timing budget apart on a fake clock. It uses the production driver options through the composition root's seam and the runtime's real 60-second watchdog timer:
- DNS wait counts against no timer, and the 15-second header timeout starts only once the lookup answers.
- The body has its own 15 seconds from the arrival of the headers.
- Retries back off 1, 2 and 4 seconds, and a `Retry-After` is honoured up to its 10-second cap.
- The watchdog reports `TIMEOUT` at 60 seconds while the driver is still retrying, and the slot is released only when the driver gives up.

Each outcome is shown arriving at its own instant and not a millisecond before.

`tests/transport/composition.test.ts` runs `startServer` itself, with its test-only seams replacing only the driver's network and resolver and the stdio entry. It shows:
- startup and discovery make no request or lookup;
- two protocol consumers share one driver identity and one budget of four calls;
- one consumer disconnecting leaves the other served, and the driver is destroyed only at shutdown;
- concurrent shutdowns share one drain;
- a write pending at shutdown is recorded as `unknown` in the `tool_call` diagnostic, and its request failing during the drain leaves no unhandled rejection;
- a connection close that rejects neither fails the shutdown nor ends it early: the drain still waits for the call in flight, the driver is destroyed and the stop is logged. The test stubs that rejection, so it shows only that the composition root absorbs a rejecting close.

`tests/transport/lifecycle.test.ts` runs the built executable against a loopback TestRail that never answers. With a request in flight, it exits with code 0 within the drain window after stdin closure, `SIGINT` and `SIGTERM`, logging one stop pair and exiting within 1.5 seconds of the `server_stopped` line. A second `SIGINT` or `SIGTERM` during the drain does not cut the shutdown short. After a staging failure, the next upload stages and is sent, and shutdown still exits 0 with nothing but JSON events on stderr. Node cannot deliver a catchable signal to a child on Windows: `kill` terminates it outright. The four signal tests therefore run on POSIX only; stdin closure, the path stdio hosts use, runs on every platform. A host that closes stdin with two catalog listings still unread, and reads them three seconds later through a shell pipe, receives every response whole (skipped on Windows, which has no `sh`). `tests/transport/composition.test.ts` holds the 250 ms grace on a fake clock, shows it does not start until stdout has flushed, and shows its timer never holds the process open by itself.

It was mutation-checked by releasing the slot as soon as the caller is answered (every capacity test fails), releasing on `result`, disposing a staged copy after dispatch, and making a late lookup start a request after the aggregate deadline. The first exposed a flaw in the tests themselves: a "still held" assertion made in the same tick the caller is answered runs before an early release could, so each now pauses first. Review found two more such checks in the cancellation suite, which a release deferred by one timer tick passed; they pause too, and that mutation now fails them. F07's closing work added three more, each of which fails an upload-staging test: staging before admission, dispatching an upload after its wait has ended, and not passing the abandon signal to staging.
