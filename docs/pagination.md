# Pagination

`src/contracts/pagination.ts` implements F06's page defaults, page metadata and aggregate control mapping. The driver's public `getAll*` helper still owns aggregation; this layer never runs a fetch loop.

## One page by default

A list returns one page of 50 unless the caller says otherwise, up to a supported maximum of 250. Explicit aggregation is opt-in through `_mcp.pagination: "all"`, which maps to the public helper's `pageSize`, `startOffset`, `maxItems`, `maxPages`, `maxBytes` and `maxDurationMs`. Absent controls default to the configured server maxima. A stated bound may lower a configured maximum but never raise it: `max_items`, `max_pages`, `max_bytes` or `max_duration_ms` above `max_all_items`, `max_all_pages`, `max_all_bytes` or `max_all_duration_ms` is refused with `INVALID_ARGUMENT` before anything is dispatched. The transport enforces this rather than the input schema, because the schemas are built when the catalog loads, before `TESTRAIL_MCP_LIMITS` is read, so the ceiling they advertise and enforce is the built-in default. A bound is refused rather than clamped so the aggregate never quietly does less than the caller asked. One consequence remains: a configured limit above the built-in default applies when the caller states no bound, but a caller cannot state a value above the default.

"All" means every remaining match from the effective `start_offset`, as far as TestRail's replies show. It is not a transactional snapshot. The reported `start_offset` is the one the caller asked for, which is also where the first request starts, rather than always zero. A reply that comes back as a bare array is the exception. The driver reads a bare array on any list as its last page, because it carries no continuation, so the aggregate stops there and still reports `complete: true`. TestRail documents three of the 24 lists that way. For `get_attachments_for_plan` and `get_attachments_for_run` the tool descriptions warn that a full reply may not be the whole list. For `get_case_statuses`, TestRail's reference contradicts itself (a bare-array example beside an envelope field table), and the description gives no such warning. On any other list, a bare array would only come from an older TestRail, which is best effort.

## Links are metadata, never fetch authority

The driver's page type supplies `_links`, not parsed controls. This layer validates a next link into caller-controllable arguments and exposes **only the validated numbers** — host and path are discarded, so the caller's original filters are reused rather than whatever the link happens to encode. The driver's aggregate does the same when it follows a link: it rebuilds each request from its own endpoint and the caller's filters, taking the link's offset, and its limit only on a response-driven list. A controlled list keeps its own page size.

Controls are read from both places TestRail puts them. A conventional link carries `?offset=50&limit=25` in the query. The real `_links.next`, however, carries **no question mark at all** — it is the fragment a client appends after its own `index.php?`, as in `/api/v2/get_cases/1&limit=250&offset=250`. A URL parse puts that entirely in `pathname` and leaves `search` empty, so reading only the query would discard every genuine continuation. Both locations are read and validated together, which also means a control repeated across the two forms is seen twice and rejected rather than silently preferred.

A continuation is accepted only with exactly one canonical non-negative offset (no sign and no leading zero, as the driver's parser also requires), at most one positive limit no greater than 250, and an offset that strictly advances past what this page already returned (`next > current` and `next - current >= returned`). Replaying or overlapping a continuation would silently duplicate items, which is worse than reporting that manual paging is unavailable.

## Saying only what was observed

`returned` comes from the items actually present; the driver's own `size` is preserved separately under `pagination.driver` rather than substituted for it. When the driver reports more data but no controllable continuation could be validated, `next_action` is `"none"`, with `has_more` still true. Advertising a manual page would mean inventing a cursor, and advising the bounded aggregate would be no better: the aggregate reads the same link through the driver's own continuation parser, and every link this layer refuses the pinned driver refuses too. That covers an invalid reference, a missing, repeated or malformed offset, a repeated or out-of-range limit, and an offset that does not advance past the page, which the driver reports as `non_progress`. Following that advice would turn a usable page into a failure with no data. A response-driven list runs the same aggregate over the same server-selected first page, so its link is validated by the same rules: it never becomes a manual page there, but a valid link advises `"all"` and a refused one `"none"`. `tests/pagination.test.ts` puts each rejection branch to a public aggregate helper, for both kinds of list, and asserts the driver's exact reason rather than comparing with a restatement of its rules, so a driver that starts following one of these links fails a test rather than leaving the advice stale.

Response-driven lists never get manual paging, even when a link parses, because their public page methods accept no caller-supplied offset.

A terminal legacy array is reported as `source: "legacy_array"` with `has_more: false` and `next_action: "none"`, and invents no `limit` or `offset` for a shape that never had them. This describes the observed response; it is not independent proof that the upstream dataset held nothing more.

## Verification

`tests/pagination.test.ts` covers both link forms, cross-form duplicates, non-canonical numbers, out-of-range limits, the advance/overlap rule, response-driven suppression, legacy arrays, empty pages (terminal, still linking on, and linking back to where they are) and the control mapping. A `next_offset` is the link's own validated offset, never one worked out from the page.

`tests/paging-through-tools.test.ts` runs all 24 paged lists end to end through `executeToolCall`, the path a client's call takes, against a two-page stand-in that serves TestRail's own link form. The inventory names the lists and the driver source names each list's envelope key, so neither comes from the registry under test. The case history is served as TestRail sends it, its envelope inside a one-element array. In page mode each list must ask for the first page (a limit of 50 from offset 0 on a controlled list, no controls at all on a response-driven one), return that page's items with no drift warning, and describe the next one: a manual `next_offset` on a controlled list, `next_action: "all"` and no offset on a response-driven one. In all mode each must follow the continuation, return both pages' items with `returned: 2` and `complete: true`, and report `start_offset` only where the caller controls it. Each list must also stop at `max_items` with `PAGINATION_LIMIT`, reason `max_items`, no data and no request for the second page; `max_pages`, `max_bytes` and `max_duration_ms` are exercised on one list of each kind, and each must report its own reason.

The F06 acceptance audit added boundary and continuation cases on one list of each kind (`get_projects`, `get_groups`), with expected values taken from the driver source (`collectAllPages`):
- Each of `max_items`, `max_pages` and `max_bytes` set exactly to what the list needs succeeds: two items, two pages, or the two pages' exact serialized item bytes in UTF-8 (the items carry multi-byte text, so a count of code units misses the boundary). One byte less stops at `max_bytes`. (`max_duration_ms` has no exact value to hit.)
- A single last page that already passes `max_items` or `max_bytes` is refused, not returned.
- `max_bytes` exactly spent by the first page stops before a second request.
- A continuation with a malformed or non-advancing offset, or a page answering an offset the aggregate did not ask for, fails as `INVALID_RESPONSE` with the driver's reason (`invalid_continuation`, `non_progress` or `invalid_page`) and no data.
- A link naming another endpoint, another filter or another host is followed only for its offset: the second request goes to the configured host and the same endpoint, with the caller's filter, and with the caller's stated page size on a controlled list or the link's limit on a response-driven one.
- An empty last page is described as finished, and an empty page that links on is followed.
- A caller's `start_offset` is where the first request starts and what is reported (on `get_projects`, since only a controlled list has one).
- An aggregate over `max_result_bytes` is refused whole, as a single read is (on `get_projects`).
- Progress counts appear exactly as the driver's helper supplies them, and a timer deadline adds none.

`tests/pagination-disclosure.test.ts` holds what each tool says, from the inventory's paging kinds. A controlled list says `Returns one page by default. Use _mcp.pagination="all" for bounded remaining matches.` A response-driven list says `Returns the server-selected first page by default; manual continuation is unavailable. Use _mcp.pagination="all" for bounded complete retrieval.` The 109 unpaged tools say nothing about pages, offsets, continuations or cursors, apart from the exact warning sentences on two attachment lists that TestRail documents no paging for. Their input schemas refuse `_mcp` and `query.limit`/`offset`. No description claims a consistent snapshot. It also scans `src/` for any import of a private driver file.

Mutation-checked: dropping the advance/overlap requirement, reporting the driver `size` as `returned`, permitting manual continuation on a response-driven list, reading controls only from the query, and hardcoding `limit`/`offset` instead of reading the page each fail a test. Through the tools, asking for a page other than the first, advising no next step, treating a response-driven list as controlled, ignoring any one of the four caller bounds or reading one as another, naming the wrong bound in the error, decoding the nested case history as a flat page, and misreporting how many items an aggregate returned each fail the end-to-end suite. The F06 audit added nineteen more, each of which passed every test before. Seven are in the adapter: an empty page read as the end or advised as `all`, a `next_offset` computed from the page, a hardcoded reported `start_offset`, stripped or invented progress, and an aggregate exempt from the result budget. Seven are in the driver: `>=` for `>` on a terminal page's items or bytes, `>` for `>=` on the bytes before another page, either terminal check removed, `max_pages` applied to the last page, and a next page fetched from the link's own path. The other five are in inputs, descriptions and imports (the paging sentence mutations are one missing and one invented): page mode accepting `start_offset` and `max_duration_ms`, a missing paging sentence, an invented one, a snapshot claim, and a private driver import. Review then found ten more that passed earlier versions of these tests:
- `max_duration` counts stripped;
- other paging wording on unpaged tools, including "paginated" and advice added inside a warned description;
- a controlled list taking the link's limit, or falling back to the driver's default page size;
- an empty page ending the aggregate;
- a malformed offset, or an unexpected page offset, reported with the wrong reason;
- aggregate bytes counted in UTF-16 code units.

The held first page in this suite's duration test is stopped sometimes by the driver's own deadline check and sometimes by one of its request timers, and both must come back as `max_duration`. A fault in recognising the timer spellings therefore fails it only in some runs; `tests/runtime-lifetime.test.ts` forces each spelling by freezing the clock and fails every time.

Two of those checks were earned the hard way. An early mutation that did *not* fail showed a hand-rolled splitter was reimplementing `URLSearchParams`, which replaced it. Review then found the remaining parser read only `url.search`, while the shape TestRail actually emits has no `?` — so it was internally consistent, tested against a fixture that TestRail never sends, and would have returned no continuation in production.
