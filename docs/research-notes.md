# Architecture research notes

Inspected on 2026-09-07. These are source observations and design implications, not accepted product decisions.

## Required-client research (2026-09-09)

The user selected Codex, Claude, and GitHub Copilot, then replaced the initially assumed VS Code surface with Copilot CLI. Local release-test surfaces are Codex desktop/CLI, Claude Code, and Copilot CLI; no server compatibility test has run yet.

- Codex supports command-launched stdio MCP servers, with command arguments, environment forwarding, and an explicit working directory. Its documented local surfaces share host MCP configuration. Default startup and tool timeouts are 10 and 60 seconds, respectively; release examples must align these with server startup and operation budgets. Server instructions should put essential cross-tool guidance first. Source: [official Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).
- A read-only local check found `codex-cli 0.149.0` and the documented `codex mcp` command surface. Claude and Copilot binaries are also on PATH; their presence is not proof of authentication, permissions, or MCP compatibility. No client configurations or credentials were read or modified.
- Claude Code supports local stdio and deferred tool discovery. Its current reference states no fixed per-server tool cap, but descriptions and server instructions have a documented 2 KB truncation boundary. Keep essential instructions concise and verify the full catalog with the selected provider/model. Even its v2 runtime has a separate stdio negotiation setting, so retain legacy protocol compatibility instead of assuming modern-only connections. Source: [Claude Code MCP reference](https://code.claude.com/docs/en/mcp).
- Copilot CLI supports local stdio, environment mappings, working directories, and `tools: ["*"]` for the complete catalog. It uses `~/.copilot/mcp-config.json`, or supported repository `.mcp.json`/`.github/mcp.json` locations; it does not read VS Code's MCP configuration. A read-only local check found Copilot CLI 1.0.67 and the documented `copilot mcp add` command. No configuration was created or changed. Sources: [Copilot CLI MCP setup](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers) and [command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference).
- Copilot CLI documents a 30-second default MCP discovery/call timeout, so its setup example must set a timeout consistent with the server's chosen budget. Tool output larger than 20 KiB is saved to a temporary file with a preview by default; compatibility checks must include access to those files and preservation of pagination and warning information. Sources: [command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) and [context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management).
- Copilot CLI's tool-search guide documents automatic deferred discovery on supported models once approximately 30 tools are available, with per-server `deferTools: "auto"` as the default. The complete 133-tool catalog is eligible for this mechanism; test the actual CLI/model combination, because support varies by model and release. Custom-agent declarations can also affect upfront loading. No CLI-specific fixed tool-count ceiling was established by the checked official documentation; this is not proof of unlimited capacity. Source: [Copilot CLI tool search](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/tool-search).
- Historical comparison only: VS Code's official tools FAQ documents a maximum of 128 enabled tools in a chat request and recommends its virtual-tools threshold setting for large catalogs. The user selected Copilot CLI instead, so this VS Code-specific constraint must not be attributed to CLI or retained as a release requirement. Source: [VS Code tool documentation](https://code.visualstudio.com/docs/agents/run/tools).

## Required TestRail driver

The local driver checkout matched upstream `main` at `89f636e276ea701412bb06039e3b963d83126ea1`. The latest GitHub release was `release/7.0.0`, tagged at `71a80d984aea14713d8eeaf6ac9a0d41c1fba12b`. Main includes unreleased network-guard fixes, so package/release behavior must be checked against the exact dependency selected for implementation.

- Package: `@dichovsky/testrail-api-client`, TypeScript, ESM, MIT, Node `^20.19.0 || ^22.13.0 || >=24`, with Zod v4 as its runtime dependency. Use public root exports; internal CLI registries are not supported package exports.
- The asynchronous client facade has 19 domain modules. Its TestRail 10.7.0 audit identifies 133 endpoint-bound methods and 48 page/all helpers. This inventory is a coverage reference, not a decision to expose every method as an MCP tool.
- The programmatic client owns HTTP authentication, network guards, timeouts, caching, retries, and TestRail pagination. An MCP wrapper should use its programmatic API directly rather than shelling out to the CLI.
- **Input validation gap:** methods such as `cases.addCase` and `cases.updateCase` validate path IDs but forward payloads directly. The CLI separately parses payload schemas. MCP must perform equivalent runtime validation at its own boundary, using exported schemas where appropriate. Some numeric payload fields require stronger ID constraints than the exported schema supplies.
- One client holds one TestRail URL and credential identity. `withTimeout()` shares underlying credentials/cache/rate state and is not an isolation mechanism. Keep process handlers disabled and let the MCP lifecycle call `destroy()`.
- No public per-operation `AbortSignal` is available. `destroy()` does not promise to abort in-flight requests. The design must accurately describe cancellation and either accept bounded in-flight completion or identify an upstream driver enhancement.
- Twenty-four lists have page/all helpers on the inspected revision, with six response-driven lists lacking caller-controlled page size/offset. Other lists lack those guarantees. Use the inspected method inventory rather than inferring pagination support from method names or the README count.
- The six response-driven page methods are `variables.getVariablesPage(projectId)`, `datasets.getDatasetsPage(projectId)`, `sharedSteps.getSharedStepHistoryPage(sharedStepId)`, `metadata.getRolesPage()`, `users.getGroupsPage()`, and `metadata.getCaseStatusesPage()`. None accepts a caller continuation offset or cursor. Their `getAll*()` helpers can follow continuation internally; initial-page plus explicit bounded-all mode is implementable without driver changes. Do not advertise resumable upstream paging through these domain methods. Other possible designs require either retaining a completed bounded aggregate for local paging, adding driver support, or taking responsibility for pagination decoding through the inherited low-level `client.request()` against fixed known routes. No such alternative has been selected.
- Aggregate reads reject partial results and bypass cache/coalescing. Driver defaults allow 25,000 items, 100 MiB, and five minutes; MCP output budgets need a separate decision. A page response retains the distinction between an envelope with continuation and a terminal legacy array.
- GET retries cover 429, 5xx, and network failures; ordinary writes retry only 429; multipart uploads are not retried. Generic MCP mutation retries would introduce duplicate-write risk.
- The client rate limiter rejects excess traffic rather than queuing it. Defaults are 100 requests/minute per client. GET caching defaults to five minutes; successful writes invalidate cached reads. Freshness and aggregate budgets must be explicit in tool contracts.
- Response entity validation is advisory and can return raw schema-drifted values. Strict MCP output schemas therefore need validated projections or additional validation. Successful writes with unusable responses can have an indeterminate outcome, which must not be reported as proof that no change occurred.
- Public errors include API, license, validation, and pagination errors. Pagination errors subclass validation errors, and license errors subclass API errors. Raw response/error/hook data may contain sensitive content and should not be copied into diagnostics wholesale.
- Attachments can be uploaded as byte/blob/file values or streamed from local files. Downloads return an in-memory ArrayBuffer, with a default 100 MiB limit. CLI file protections do not automatically apply to SDK consumers. Attachment IDs can be numeric or UUID strings; plan-entry IDs are UUID strings.
- `attachments.getAttachment()` returns only bytes, without filename, media type, or response headers. A local-file download result can truthfully provide the attachment ID, generated local path, and measured byte count; an original filename or media type requires additional verified metadata and must not be invented. The accepted file-based MCP design owns permitted directories, symlink/containment rules, unique naming, overwrite behavior, failed-write cleanup, and file lifetime. Returned local paths require a consumer with access to the same filesystem. See the accepted [attachment workflow](architecture.md#attachment-files).
- Case, Test, and Result data may carry flat `custom_*` properties with unknown values. Metadata exposes custom-field definitions. MCP schemas must retain these distinctions if those operations are included.
- Injected `fetch` and `dnsLookup` provide a testing seam for a real driver with deterministic upstream responses. Adapter tests should focus on MCP mapping, validation, policy, and output contracts; the driver already tests transport behavior.

## MCP baseline

- The official SDK identifies v2 and MCP 2026-07-28 as stable. The released server package is `@modelcontextprotocol/server@2.0.0`; the client package is `@modelcontextprotocol/client@2.0.0`. Node HTTP hosting has a separate `@modelcontextprotocol/node` adapter. The server package requires Node 20 or later; the TestRail driver's requirements must also be satisfied.
- The modern protocol replaces the initialization handshake with discovery and per-request metadata. Client compatibility must therefore be tested deliberately rather than assuming that all clients implement the same protocol generation.
- Released v2 `serveStdio(factory)` supports older clients by default. `createMcpHandler(factory)` supports modern HTTP and stateless legacy compatibility by default. `legacy: 'reject'` disables that compatibility.
- Stdio is a host-launched subprocess transport. Standard output must contain only protocol messages; diagnostics belong on standard error.
- HTTP hosting adds authentication, Host/Origin validation, credential isolation, and service lifecycle responsibilities around the SDK handler. The handler does not implement those policies itself.
- Tool input schemas, structured outputs, and deterministic discovery belong at the MCP boundary. Output schemas must describe what is actually returned. Text containing serialized JSON can support older clients alongside structured output.
- Read-only, destructive, idempotent, and open-world annotations describe tools; they do not enforce authorization or require a host to obtain confirmation.
- API/business/input failures should be represented as tool errors; malformed protocol requests and unknown tools are protocol errors.
- SDK tool handlers receive an abort signal. Propagation depends on driver support; cancellation cannot undo an already accepted TestRail write.
